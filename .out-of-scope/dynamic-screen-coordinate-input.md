# 动态界面下的坐标输入（tap / swipe / touch）

DSHA 的虚拟屏坐标与文本输入要求调用方带上“刚看过、且仍是最新”的帧号；帧间隔短于一次
`see` → 输入往返的界面（大致 20–60fps：首页轮播、直播小窗、loading）因此**不可能**通过坐标
输入操作。这个限制是**有意保留**的，不是待修的缺陷。

## 为什么不做

坐标的含义是“画面 X 处当时有个按钮”。一次 HTTP 往返（本机几十毫秒）长于帧间隔时，调用方
手里的坐标描述的是**已经过去的画面**：

- 页面在往返期间跳到支付页、切到另一个 tab、弹出遮挡层，坐标就落到别的东西上；
- 这类误点没有“操作失败”这种轻量后果 —— 它可能完成一次支付、发出一封消息、确认一个删除。

`util/VirtualScreenPolicy` 因此把帧门写成“必须等于最新帧”，而不是“不早于最近 N 秒”：后者给
调用方留的误差预算，正好是误点发生的窗口。真机上的 22 次实测（#116）显示动态界面下坐标输入
命中率 0% —— 这个 0% 是设计结果，不是 bug。

## 动态界面怎么办

用语义操作：`tree` 读控件树 → `node` 按 `nodeId` 做 `click` / `long_click` /
`scroll_forward` / `scroll_backward` / `focus` / `set_text`。

- 与“当前第几帧”无关，不需要 `frameSeq`；
- 不回传图片，token 成本远低于截图循环；
- 安全性由无障碍层承担：树必须 ≤30 秒内（`STALE_TREE`），节点必须还能 `refresh()` 且窗口
  一致（`STALE_NODE`）。控件消失时无障碍框架自己返回 false，不会点到别处。

也就是说，“操作稳定”与“token 可控”在语义操作这条路上同时成立，不需要放宽坐标帧门。

## 曾经被要求过

- **#116**（`not planned`，2026-10-09 关闭，未留评论）：“虚拟屏内持续渲染的应用（≥1fps）无法
  输入：tap/swipe/type/key/node 恒报 STALE_FRAME”，附 22 次实测与静止界面对照。该票的 `node`
  部分已在 #117 / PR #134 修掉（语义操作不再套像素门），坐标注入部分维持现状。
- **#117**（2026-10-10）：同一诉求重报，多了 token 成本与生态对照（BigBirdUI 不校验帧号）。
  分流结论同样是“坐标帧门不动”，`node`、错误码粒度、文档与诊断输出部分已修。

## 什么时候可以重新讨论

需要的是**能证明“这一帧的坐标仍然有效”的机制**，而不是把帧门调松。例如：

- 调用方能证明目标窗口或节点自取帧以来没有变化（类似 `node` 的 `refresh()` + windowId 校验，
  但坐标没有节点身份可比）；
- 输入前原子地冻结画面（`freeze` → 输入 → `resume`），使“往返期间画面变化”不可能发生；
- 或者另开一条不依赖受信任显示的通道（例如 MediaProjection 形态的应用作用域）。

第一条是当前形态下可行的方向；后两条是新功能，需要单独立项。
