# 接手 DSHA：给不懂安卓开发的人和他手里的 AI

这份文档假设你**不会安卓开发**，也不打算学。你要做的事是：把需求说清楚，让 AI 写代码，然后
判断它写得对不对。下面是这个项目运转起来所必需的那些知识 —— 通用的 Android 教程网上都有，
这里只写**这个项目特有的、不知道就一定会栽**的部分。

写这份文档的依据是真实的开发过程：把一个 7785 行的巨型类拆开、重做插件安装链路、
以及在这个过程里踩出来又修掉的三十几个 bug。第 4 节那些坑，每一条都真的发生过。

---

## 0. 这个项目是什么

三句话：

1. **dsh**（DeepSeek Harness）是 DeepSeek 官方的 agent 框架，跑在 Node.js 上，本来只能在
   电脑上用。
2. **DSHA** 把一个完整的 Ubuntu 24.04 环境（含 Node 24 和 dsh）塞进安卓 App 里，
   用 proot 这类工具在**没有 root 的手机上**把它跑起来。
3. 所以 DSHA 的本职是**宿主**：装环境、起进程、把安卓的能力（悬浮窗、通知、ADB、
   无障碍、文件系统）接给 dsh，以及在出问题时能自愈和恢复。

用户看到的是一个 App：点开、等环境就绪、里面显示 dsh 的网页界面（WebUI），
可以像用 ChatGPT 那样对话，而 agent 能真的在手机上跑命令、读写文件、操作别的 App。

技术上分三层，改任何东西之前先想清楚要改的是哪一层：

```
安卓原生界面（Java + Material3 + GeckoView 浏览器内核）
        ↓ 调用
HarnessController —— 业务核心，App 与容器之间所有事都从这里过
        ↓ 执行命令
proot/proroot 容器 —— Ubuntu 24.04 + Node 24 + dsh
        ↓ 提供
三个本地端口：3080（dsh 的网页界面）· 3090（App 桥，agent 用它调安卓能力）· 3081（局域网）
```

## 1. 第一天：把环境跑起来

### 1.1 编译（这两个参数必须写成同一个值）

```sh
export GRADLE_OPTS="-Xmx1280m -Dfile.encoding=UTF-8"
gradle :app:compileDebugJavaWithJavac --no-daemon --no-parallel --offline \
       -Dorg.gradle.jvmargs="-Xmx1280m -Dfile.encoding=UTF-8"
```

`GRADLE_OPTS` 和 `-Dorg.gradle.jvmargs` **必须是同一份值**。不一样的话 Gradle 会另外
fork 一个 JVM（于是同时吃两份内存），在内存紧张的机器上直接被系统杀掉 —— 而报错看起来
像是"编译莫名失败"。这条是实测出来的，不是理论。

改完代码**每次都要编译**，不要攒着。改了界面文件（`res/layout/*.xml`）还要多跑一个：

```sh
gradle :app:processDebugResources --no-daemon --no-parallel --offline -Dorg.gradle.jvmargs="..."
```

### 1.2 三个测试脚本（不需要手机，跑得很快）

```sh
bash tools/pure-logic-test.sh      # 纯逻辑断言，目前 246 条
bash tools/archive-e2e-test.sh     # 造真实压缩包跑一遍，16 条
bash tools/restore-scope-test.sh   # 备份恢复的范围判定，19 条
```

**这三个脚本是这个项目最值钱的东西。** 它们不需要手机、不需要容器，几秒钟跑完，
却抓住了很多只看代码看不出来的错。让 AI 改完代码后必须跑一遍，红了就是真的错了
（也有可能是测试自己写错了 —— 那也得当场弄清楚，假失败和真失败一样费时间）。

**每加一个功能，就往里加断言。** 判断该加什么断言的标准是：
"这条规则如果哪天被人不小心改坏了，用户会怎么倒霉？" 越倒霉的越要写死。

### 1.3 出安装包

```sh
bash tools/pack-local.sh
```

七个阶段（预检 → rootfs 就位 → 清单签名 → 编译 → 打包 → 验签 → 命名）。每段完成会落一个
标记，中断了重跑会自动从断点继续。想重打某一段加 `--force`：

```sh
bash tools/pack-local.sh --only 4 --force    # 只重新编译
bash tools/pack-local.sh --only 5 --force    # 只重新打包（最慢，全量约 7 分钟）
bash tools/pack-local.sh --from 6 --force    # 验签 + 命名
```

包大约 373MB（里面装着整个 Ubuntu 环境，所以这么大是正常的）。

## 2. 代码地图：改东西该去哪

```
app/src/main/java/com/deepseekharness/app/
├── HarnessController.java     业务核心（约 6200 行，仍然偏大）
├── PluginController.java      插件的一切：市场、安装、启停、导入导出
├── BackupManager.java         备份与恢复
├── ProotBootstrap.java        容器怎么起来
├── HttpShellService.java      3090 桥，agent 调安卓能力的入口
├── *Fragment.java             各个界面
└── 一堆小类 —— 见下面
```

**那些小类是刻意拆出来的**，它们的共同点是：**纯逻辑、不碰安卓 API、因此能被断言覆盖**。

| 类 | 管什么 | 为什么单独拆出来 |
|---|---|---|
| `ShellQuote` | 把字符串安全地拼进 shell 命令 | 树里**唯一**一份转义实现。插件市场上的名字会一路进到 `bash -c`，这里错了就是命令注入 |
| `Query` | 解析 URL 查询串 | 唯一一份。以前各处自己 `indexOf("key=")`，任何以目标参数名结尾的参数都会劫持它 |
| `PluginSpec` | 认识"插件从哪装"的所有形态 | npm / jsr / git / tarball / 本地路径…形态很多，判据必须集中在一处 |
| `PublicDirs` | `Download/DSHA/` 下的目录布局 | 写入这个目录的代码有三处，路径各自硬编码就一定会漏掉一处 |
| `ArchiveProbe` | 认压缩包格式与里面的插件布局 | 按文件头判而不是按扩展名 —— 用户挑的文件叫什么都有可能 |
| `PatchToggle` | 生成插件开关要写的配置片段 | 它改的是**用户自己的**配置文件，写坏了整个 dsh 起不来 |
| `GitHubRef` | 解析 GitHub 链接 | 以前两处各写一套截断逻辑，其中一处把子目录丢了 |
| `BackupScope` | 备份的三种范围 | 文件名前缀是安全关键，判据必须唯一 |

**新增功能时的默认动作**：能抽成纯逻辑的部分就抽出来单独一个类，然后写断言。
安卓相关的那层（界面、权限、文件系统）留在原处，那部分只能真机验。

## 3. 职责边界：什么该做，什么绝对不做

**这一节是这份文档里最重要的一节。**

> **dsh 本体已经有的东西，DSHA 一律不做。**

DSHA 是 dsh 的宿主与安卓集成层，**不是第二个 agent 内核**。

**归 dsh 的（别碰）**：权限档位 · 会话记录与恢复 · 对话历史压缩 · 技能（skills）机制 ·
任务调度 · 模型与账号管理 · MCP · 记忆 · 消息分支。

**归 DSHA 的**：环境宿主（容器、rootfs、升级）· 安卓集成（悬浮条、通知、ADB/Shizuku、
无障碍、终端、三个端口的桥）· 凭据与配置 · 备份恢复与自愈 · 插件市场与内置插件安置 ·
更新与签名。

借鉴别的项目时先过这道筛子。真实教训：曾经提过"给工具加三档权限"这种建议，
而 dsh 早就有了 —— 那是在造第二个轮子，被否掉了。

## 4. 这个项目反复栽的八个坑

每一条都真的发生过，而且**大多不止一次**。让 AI 写代码时把这几条贴给它。

### 坑 1：同一份判断散落在多处（头号模式）

出现频率远超其他所有问题。典型现场：

- 解析 GitHub 链接有两处实现，其中一处把 `/tree/main/plugins/x` 这段丢了 →
  用户装的是整个仓库而不是那个插件，**而且提示"安装成功"**。
- 网络请求有个 512KB 的大小上限。市场索引超过这个大小，被静默截断 → 解析失败 →
  悄悄退回旧路径。修好这一处之后，**下一轮又在另一处同样的调用上踩了一遍**。
- 注册内置插件的代码有三份逐字拷贝，改一份另两份还是老的。

**做法**：写新代码前先搜一遍"还有谁在做同样的事"。修 bug 后再搜一遍"还有谁会犯同样的错"。
判断只有一份实现时，就把它抽成一个类并写断言 —— 这就是第 2 节那张表的由来。

### 坑 2：兜底写得太顺手，把功能失效藏起来

```java
try {
    用新的、更好的那条路;
} catch (Exception ignored) {
    退回旧路径;      // ← 用户永远不知道新路径从来没成功过
}
```

真实案例：市场索引换成一份更好的数据源（带 npm 包名映射），但因为上一条那个 512KB 截断，
它**一次都没成功过**，而旧路径能用，所以表面一切正常。这种 bug 只有专门去查才发现得了。

**做法**：兜底要留痕（写日志、或在界面上说明"用的是备用方案"）。
"静默降级"和"没做这个功能"对用户是一样的，但对维护者更糟 —— 你以为它在工作。

### 坑 3：只看命令退出码，不看实际状态

`pnpm install` 返回 0、日志里写着"装了 2 个包"，但插件在界面上根本不出现。
原因是安装成功≠注册成功，而我们只检查了退出码。

**做法**：做完一件事，**去查那件事该有的结果在不在**。
装完插件就去看它有没有真的进配置清单；备份完就去看包里有没有对话。
这个项目现在到处是这种"眼见为实"的复查，都是被这类问题逼出来的。

### 坑 4：转义层数

```java
// Java 源码里这么写：
"printf 'registry=https://registry.npmmirror.com\\\\n' > /root/.npmrc"
```

Java 字符串脱一层、shell 脱一层、printf 再脱一层 —— 最后写进文件的是**字面的反斜杠 n**，
于是那个地址变成了 `https://registry.npmmirror.com/n`，**所有联网安装都 404**。
更阴险的是：包已经在缓存里时不查网络，所以这个 bug 藏了很久才暴露。

**做法**：拼 shell 命令时，能用简单形式就别用带转义的（这里用 `echo` 就没事）。
拼完之后**实际跑一遍看输出**，别靠脑内推演数反斜杠。

### 坑 5：在界面线程做文件读写

安卓有个硬规矩：界面线程卡住超过几秒，系统直接弹"应用无响应"。
插件开关的实现里读写了好几个文件，一直放在界面线程上 —— 插件多、存储慢的时候就是个雷。

**做法**：任何文件、网络、执行命令的操作都放后台线程，界面先乐观更新、失败再回滚。

### 坑 6：改并发模型时忘了随之出现的共享状态

把插件开关改成后台线程之后，立刻多出两个问题：
连点两个开关 → 两个线程同时"读改写"同一个配置文件，**后写的把前一个盖掉**；
以及回滚时重新设置开关状态会**再次触发监听器**，一次点击变成两次相反的操作。

**做法**：把某件事改成异步/并行时，当场问三句：谁还会同时碰这块数据？失败回滚会不会
触发新的事件？重复执行一次会怎样？

### 坑 7：合成的测试数据过了，真实输入不过

判断压缩包里插件位置的逻辑，用手写的路径字符串测得好好的。后来写了个脚本造**真实**的
压缩包再跑一遍 —— 立刻发现从 GitHub 下载的 monorepo 压缩包会被装成"仓库的管理包"，
真插件一个都没装，**而且还是"安装成功"**。

**做法**：涉及外部数据格式（压缩包、网络响应、别人的配置文件）的功能，
一定要拿**真实样本**跑一遍。`tools/archive-e2e-test.sh` 就是干这个的，照着加。

### 坑 8：这台机器上没有"后台任务"

容器是用 `--kill-on-exit` 起的：一次命令调用结束，这次调用下面的所有进程连根被杀，
`nohup` 和 `setsid` 都逃不掉。所以别写"先在后台启动，过一会儿查日志"那种流程 ——
长任务必须在一次调用内跑完（上限约 10 分钟），或者靠工具本身的增量能力分几次续跑。

另外容器里能看到手机上所有进程，`pkill -f node` 会连 App 自己一起杀掉（表现是点一下
过十秒钟闪退）。杀进程必须先确认目标是谁。

## 5. 和 AI 协作的规矩

这些是从几十轮实际协作里定下来的，直接说给 AI 听。

### 5.1 给 AI 的固定要求

1. **每轮改完就 commit**，提交说明用中文写清**根因和取舍**，不要写"修复了一个 bug"。
   这个项目的提交历史现在是最好的文档，因为每条都写了"为什么这么改"。
2. **每轮改完必须编译 + 跑那三个脚本**。没验证过的代码不算写完。
3. **遇到问题先搜一下有没有同类方案**，不要自己一直试。真实教训：某个插件装不上，
   查了官方文档发现作者自己在说明里写了正确的装法，而我们之前一直在猜。
4. **一次多给几个备选方案**，不要只赌一种做法然后让人当测试员。反例：某个功能改了六版，
   每版只试一种思路，装了七八次包。
5. **反复修不好的问题去查提交历史**（以前是好的，那就二分找出哪一次改坏的），不要继续猜。
6. **不要反复请示**。"要不要出包""要我继续吗"这类问题一律别问 —— 直接做完再报告。
7. **界面上不要堆常驻入口**。一年用几次的操作放进对话框或已有入口（比如长按），
   不要在设置页新加一行。

### 5.2 判断 AI 做得对不对（你不懂代码也能判断）

- **它说"修好了"的时候，问它验证了什么。** 答不出具体验证手段的，大概率没验。
- **它改完之后断言数应该变多**（246 → 更多）。功能加了而断言没加，就是留了雷。
- **看它的提交说明里有没有"为什么"。** 只写"改了什么"的，说明它没搞懂根因，
  很可能只是让症状消失了。
- **它说"这个改动需要真机验证"的时候，认真对待。** 界面、权限、文件系统、
  手机厂商定制系统的行为，在电脑上验不出来，只能你去点。
- **它主动说"我这里判断错了"或"上一版是我判早了"的时候，那是好事。**
  真实案例：某个插件被判定为"装不了"，后来翻作者的说明发现只是需要先构建一下 ——
  纠正这个判断之后功能就通了。

### 5.3 怎么描述需求

好的需求描述长这样（都是实际提过的）：

> 在插件管理栏的插件卡片上加一个导出按钮，点击后导出此插件到
> `/storage/emulated/0/Download/DSHA/插件/`，形式为单文件。

有位置、有动作、有落点、有形态。AI 不用猜。

不太好的描述是"优化一下插件管理" —— 这会让 AI 自己发挥，做出一堆你没想要的东西。

如果实在只有一个模糊的想法，就说清**你想解决的问题**（"很多人反馈市场里大部分东西装不了"），
让 AI 去查根因 —— 那次就是这么找到四个独立的真 bug 的。

## 6. 发版与签名（两把钥匙，别搞混）

这个项目有**两把不同用途的密钥**，混用会造成用户装不上包或者拒绝更新：

| 密钥 | 干什么用 | 混用的后果 |
|---|---|---|
| 一份 debug keystore（证书指纹 `E7:E3:A3:1A…`） | **给 APK 签名**。线上所有正式包都是它签的 | 换了它，用户就无法覆盖安装，只能卸载重装 —— 而容器数据在 App 私有目录，卸载就全丢 |
| `DSHA-release.keystore`（指纹 `ED:8A:AE:A2…`） | **只签"运行时更新清单"** | 用它签 APK 会造成上面那个后果；反过来用错的钥匙签清单，客户端会整批拒绝更新 |

**安卓只允许同签名覆盖安装**，所以那份 debug keystore 绝对不能丢（它是构建工具自动生成的，
清一次 SDK 目录就会重新生成一个不同的，指纹一变以后的包就再也装不上了）。
备份放在工作区里，别删。

发版只需要一条命令：

```sh
git tag v1.1.9 && git push origin v1.1.9      # 触发 CI 自动构建并发布
```

带连字符的标签（`-rc1`、`-fix`）会被自动标成预发布版，**不会推给普通用户**。
想给人试用就用这种标签。

## 7. 卡住了怎么办

**编译过不了** → 先确认第 1.1 节那两个参数写成了同一个值。

**测试红了** → 先弄清是代码错了还是测试写错了。两种都有过，别默认是哪一种。

**功能在电脑上看着对、真机上不对** → 大概率是这几类：
文件系统限制（App 私有目录不支持硬链接、软链接时好时坏）、
权限（安卓的文件访问规则每个版本都在变）、
手机厂商定制系统的行为差异。这类只能真机验，所以**选不需要赌的实现方式**
（比如用复制而不是建链接）。

**某个功能怎么改都不对** → 去翻提交历史，找出它上次好用是哪个版本，二分定位。

**不知道该不该做某个功能** → 回到第 3 节那道筛子：dsh 是不是已经有了？

**要出包给人试** → 第 1.3 节，三条命令。包名里带 commit 短哈希，
所以拿到包能直接对上代码版本。

## 附：一句话总结这个项目的开发哲学

**任何"判断"都只能有一份实现，任何"完成"都必须有可执行的证据。**

这两句话涵盖了第 4 节里八个坑中的七个。剩下那一个（没有后台任务）是环境限制，
记住就好。
