# build155 架构定性与技术债边界

当前设计是单 Gradle 模块中的 Android 宿主编排架构：原生界面与设备权限围绕应用生命周期，proot/proroot 承载独立 Linux/Node 运行域，宿主数据事务负责原件、候选和提交。单模块并不意味着没有边界，拆出更多文件也不自动证明业务解耦；判断应看状态谁拥有、输入是否固定、未知退出时能否继续保护数据。

核心亮点是受管组件与个人数据分离、可回切的候选事务、独立应急运行根、以及按出生身份而非裸 PID 确认进程。本轮继续把 Web 状态从控制器静态散列收敛到应用拥有者，同一应用的旧门面仍共享唯一代次与队列；桥接端点改为明确路由，冷安装与输出收集拆出协作者。它们改善的是职责归属和可验证行为，而不是单纯减少某个类的行数。

复杂度和“屎味”主要来自四处：多语言之间依赖精确补丁、字段与资产摘要；Android 文件别名、权限、进程访问和浏览器行为存在平台差异；历史格式需要读取但不能假定可以安全删除；源级门禁曾依赖格式空白和未区分机器生成类。预检已经捕获并修复了生成字节/格式冲突、夹具缺少新依赖，以及短暂 DNS 信息缺失会清空受管配置的真实回归。保留这些失败证据比只显示最后的通过数更有助于定位风险。

本轮样式范围为 702 个明确自有 Java 项，固定格式工具和真实编译器 token 证明配合使用。两个机器生成类保持生成器规范字节，另一个来源待核实的原件保持原字节；这些排除有来源和清单，不能说成遗漏已经通过检查。软件执行证据由最终交付报告绑定，不能将旧 build154 的通过回执当成 build155。

有意保留的合同包括历史备份读者、完整摘要/源核验、未知进程退出屏障和不可确定记录的原件。它们有维护成本，但删除会损害功能与数据保护。ProotBootstrap 的插件、维护与 PTY 入口仍较密集；当前组合根的全局运行端口仍代表一个进程的宿主适配器，不能据此宣称已经完成全面依赖注入。后续拆分应围绕明确的调用与覆盖证据，不应凭“类很长”继续无限改动。

真实后台/浏览器/Root/Shizuku/OEM/FUSE/覆盖安装行为仍需要设备证据。Linux 发布夹具在本轮实际使用可写 tmpfs，通过了真实内核调用与并发发布测试；这不能替代 Android FUSE 或持久化/掉电验证。来源授权未知和损坏的历史摘要也不能由源码重构解决。

因此，本轮不以条目关闭率、类数量或代码行数推导“低于 20”的分数。最后应交付确定的源码与正式 APK、逐项处置、实际验证和保留范围；完成已授权本地交付后停止。
