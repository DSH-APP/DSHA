# DSHA 0.2.1-rc.3 / build196：启动准备、悬浮助手与文件操作修订

本轮处理重复启动准备、悬浮助手接入与状态刷新、普通工具被原生确认查询连带阻断、分享被显示或降级为下载，以及新旧 DSHA 同时安装时的端口共存问题。补充真实会话/轮次绑定、屏幕遮挡范围和 Web 实例记录的诊断。修订的软件范围与最终手机验收分别记录，不把宿主夹具通过写成手机业务完成。

当前标准候选为 `0.2.1-rc.3-20261024.1835-dsh0.2.1-rc.3` / code196 / `dsh.android.client` / E7E3 / 非调试。正式与独立应急 DSH 均为 `0.2.1-rc.3`，Ubuntu base10 和既有本机引擎选择保留。

最终 R7 标准候选为302,430,394字节，SHA-256为`f3e053866dbf410edfc02587d64c9589ce9ac3c702f5bdef751b1f501c708d57`。R6原候选为302,430,410字节，SHA-256为`876d9cd71c6839d2a3179bd8f8bfc06a348cae58dd3e548147743c43a748ca75`。R7仅修正一处草稿标签的双语完整模板，R6实际设备结果保持其原始归属。R7的最终软件、装机及交付回读见末表与外部回执。

## 启动与入口

普通启动原先依次注册内置插件、迁移旧插件标记，两次入口各自准备运行环境、Python、pnpm 和随包工具。本轮把这一组共同准备合并到当前启动范围内执行一次，再按原顺序分别派发两个原有有界 guest 命令。后续独立插件命令仍重新准备，不跨启动缓存可变文件、stat 或内容证明。

完整安装核验、CAS 检查、旧数据事务、RC1 迁移、内置注册、旧标记迁移及停止屏障继续执行；不能以准备去重跳过旧 guest 与 launcher 的退出核验。新增 `STARTUP_PREP_TIMING` 使用单调时钟记录各准备阶段，进入既有有界启动 trace/history；方法返回不等于事务或业务成功。

桌面图标回到原生 Main 首页，电脑工作区改为首页完整宽度入口；未初始化本机环境的电脑入口继续独立，不为进入电脑工作区启动本机 Ubuntu。移除首页工具栏的后台任务按钮；原有本机启动、通知入口、初始化及浏览器恢复门禁保持各自职责。

同一设备的195单次暖启样本，后端鉴权约3.1秒。R4更新后的首次后端鉴权约5.4秒；正常停止后再次暖启，后端鉴权约2.9秒，另记录load阶段约1.5秒。最终R6更新后首次后端鉴权约5.4秒、服务约5.5秒、load约2.0秒；正常停止后的暖启后端约3.2秒、load约1.7秒，实际4.422秒的截图已显示READY。这些是不同条件和阶段的单次样本，不作整体提速比例，也不把后端鉴权、load和模型首字混成一个耗时。R6与195约3.1秒的暖启样本接近，不能宣称总体明显加速。195和R6均观察到模型列表请求约5秒超时后使用随包目录；准备去重不能证明该模型服务延迟已经修复。历史较长的BROWSER_READY间隔还包含人工在Main停留及稍后进入网页，不能当作纯网页加载测速。

## 悬浮助手、会话归属与普通工具

本机助手入口在读取会话前请求只读恢复已运行的 Web 实例，并随真实就绪身份变化及页面恢复刷新。连接绑定完整页面身份，而非仅看一个非空地址或旧代次。界面分别提示未启动、正在核对、连接已变或接口暂不可用；未知发送/取消结果仍须核对会话，不自动重发业务。会话列表、草稿、回复和取消始终使用具体主机及完整会话 ID。

实体屏 MCP 工具从当前真实 DSH 执行上下文传递完整会话和轮次，不使用全局“最后活跃会话”、模型自填身份或统一的 `local-session` 兜底。当前轮结束只退休其自身控制权；迟到的结束事件不能清掉新轮任务。暂停、停止及继续仍围栏旧请求，继续后必须重新观察屏幕。宿主回归覆盖同尾缀不同会话、并发争用、连续两轮、迟到结束、错误任务暂停和恢复后的新观察要求。

工具策略原先在每一类工具准备和派发时都要求原生全局确认查询有效；回复解析失败会连带阻断普通读取、传输和安全 Bash。现在只有写入/编辑/替换以及既有分类器判定为危险或不透明的 Bash 使用该破坏性操作证明。普通读取和分类器安全 Bash 保留执行身份、取消、服务提供者及底层权限检查。原生 ON/OFF、正式完整权限预设撤销、一次性许可和文件 CAS 在其使用路径继续核验。

这修正了错误扩大的依赖范围，不证明原反馈中 `INVALID_REPLY` 的具体无效字段已经找出。195已有真实模型及只读工具的有界成功样本；196 R3 已通过原生助手真实键盘发送及模型对话，并实际调用读屏工具。模型有回复不等于已经执行工具，R3的工具结论使用工具详情另行核对，也不能据此宣称原反馈全部路径恢复。

助手 HTTP 夹具最初直接构造 Cordis Service，造成测试作用域注入失败。改成真实锁定 rc3 插件装配后，已挂载的实际接口通过6项会话列表、创建、发送、取消、鉴权和来源检查；未把夹具装配错误写成正式接口缺失，也没有为此保留推测性的生产注入修改。这些宿主检查未向模型发请求。

手机验收另发现两处宿主检查未能代替的故障：R1 更新受管环境时缺少 `session-adapter.js`，实际报 `MODULE_NOT_FOUND`；补齐内置插件部署清单的两个 helper 后，R2和R3实际更新通过。R2 悬浮助手编辑框的焦点问题在 R3 修复后完成真实键盘输入及模型对话检查。失败候选和原始记录保留，不将后续修复通过写成首轮无故障。

R4长会话又暴露输入区随历史记录落到多屏之后的问题。最终生产Activity将消息历史与固定输入区分开布局，长记录和IME场景由实际Activity的JVM检查覆盖；`junit-r7-final`通过后，R6相同Java输入再以`junit-r8-final`完成45类279项复跑。最终R6在负责人新建的测试会话完成多轮真实模型对话、长记录下输入区持续可见、键盘输入及发送；编辑时自有悬浮层隐藏，历史记录独立滚动。结束时通过实际“结束悬浮助手”按钮关闭助手，未修改用户原有对话。

## 分享、另存为与下载

已确认的三处问题分别是：分享请求也显示“已添加到下载”；持久分享任务核验后没有自动打开选择器，只能稍后从记录页手动操作；旧 Blob 分享不支持或失败时会静默转成保存。

本轮让明确的“分享”和“另存为”在文件核验后进入对应前台原生界面，自动打开本次请求的分享选择器或系统文档选择器。自动派发绑定当前顶层文档、原生 owner、任务、目标及前台状态，派发前消费本次待办；后台、终止错误或进程身份丢失后不补发旧操作。分享使用 `ACTION_SEND`、内容 URI、精确 MIME 和临时只读授权，失败不转成下载。

下载/保存的单文件上限仍是十进制 `5,000,000,000` 字节；明确的原生分享上限为32 MiB，超限给出可操作说明。`queued` 只表示入队，`chooser-opened` 只表示选择器打开；都不表示收件应用已接收，也不表示 SAF 已最终落盘。

R2 在实际 Android16 上打开了分享选择器，另存为和下载分别完成9字节 `HELLO196\n` 的最终字节回读。最终R6另新建`FINAL196.TXT`重复验收：分享自动打开系统选择器，显示文件名和9字节，随后取消；另存为自动打开DocumentsUI并保存至Download，默认下载保存至Download/DSHA。两处实际文件均回读为9字节`HELLO196\n`，SHA-256为`b83c95e64bd30617905aa869485077b84902771ed7b676ec5a4d1f6e6a3a740d`。分享选择器打开不扩写为接收应用完成接收，未以小文件结果推断手机5GB或重启续传已通过。初次自动化导航实际打开预览而未请求下载的材料也保留；重新观察并点击下载后才记录文件回读成功。

宿主浏览器已覆盖实际锁定 rc3 的移动 React 控件、随包 Blob/产物桥、本机鉴权 gzip prepare/resolve/content、图片/Unicode/空文件字节及远程文件桥。部分初始失败来自简化夹具层遮住控件，修订与原失败材料均保留；最终浏览器通过不代替 Android 选择器或接收应用验收。

## 双安装端口、屏幕与 Web 记录

当前包的原生桥优先使用3091–3099，再尝试3090；旧包保留3090优先。当前包 LAN 优先3082，留出旧3081；仅明确地址占用时直接绑定动态端口，并持有实际返回的 socket。显示和复制的 LAN 地址来自当前已鉴权 Web 代次的实际端口。Web 配置、保存端口和启动地址排除3081、3082及3090–3099，避免把设备桥或 LAN 端口当作 Web。分配只靠实际绑定，不探测端口归属或按 PID/名称杀进程。

宿主检查实际运行了隔离应用类加载器、独立监听端及后端，覆盖两种启动顺序、同端口竞争、跨 token 拒绝和各自停止。手机另完成R4与已安装legacy190（`com.dsh.client`）的有限共存：当前包Web35171/bridge3091，旧包Web44011/bridge3090，两者同时READY。正常停止旧包后，44011和3090消失，当前35171和3091保持，当前Main仍为READY。该结果只覆盖这台手机、这两个安装与本次停止路径，不外推为所有双包组合或长时共存矩阵。

屏幕观察新增同次返回的窗口、可用内容区、遮挡及排除区几何信息。仅精确匹配自有包、已登记窗口 ID、测量范围和发布代次的收起控件可成为排除区；匹配后排除整个当前原生窗口，不能把装饰边缘当可点击区。系统边缘栏/输入法只按完整边缘裁剪，内部或未知遮挡继续拒绝坐标控制。新元数据不授予触控许可；`effectVerified:false`、未知执行结果和过期观察仍不能重放。

R3真实工具详情中，`android_get_state`返回`ok=true`及`COMPLETED` / `SCREEN_COMPLETED`，包含正确的Workspace树；后续两轮再次读屏成功。设置页操作曾被实际Web画中画窗口遮挡门拒绝，该窗口与自有悬浮助手不同。R4实际模型进一步确认当时MCP未暴露`android_node`，最终通过坐标操作完成设置页滚动；该结果属于坐标操作，不记录为语义滚动通过。

最终R6在真实`server.cjs`补出`android_node`，接入现有`/app/ui/node`，支持点击、长按、前后滚动和聚焦，并继续由实际执行上下文提供任务身份。`android-node-change-receipt.json`记录22项实体屏夹具，其中实际MCP→HTTP→生产Java链调用4096/8192无障碍动作，旧节点拒绝、`UNKNOWN`保留，坐标手势为0。另在最终R6真机实际模型轮次中，`android_node`以当前treeId/nodeId执行`scroll_forward`，原始返回为`ok:true`、`COMPLETED`、`ACCESSIBILITY_NODE_ACTION`及动作4096；后续复读与独立屏幕截图确认设置列表向前滚动一页，没有点击或修改设置。该轮没有坐标手势。接口返回仍如实为`effectVerified:false`，效果由后续观察确认，不能改写接口承诺。

Web 实例记录原先把原始 `getNoBackupFilesDir()` 直接交给严格 NOFOLLOW 文件系统。在存在 Android 框架父目录别名的受控夹具中，这会产生 `PARENT_LINK`。现在仅解析框架提供的应用数据根，再绑定确切 `no_backup` 子目录并核对目录身份；应用可写子链接、外来父目录和替换 inode 继续拒绝。当前Android16的目录元数据未证明存在这一别名，不能把历次 `IOException` 都归因于它。

新增固定白名单错误码和阶段诊断，区分 guest/launcher、环境、boot、记录捕获、加密存储及恢复失败，不落出自由格式异常、路径、令牌或环境值。boot、PID出生、UID、环境身份、鉴权及 guest/launcher 退出证明要求没有放宽。
