> 本文绑定 build328 的源码改动，只报告实际执行过的检查。正式包的构建、单测、签名与发布结果以本版 CI run 与 Release 回执为准；

## 1. 事故与根因

用户报告：在 0.2.2-rc.1 环境执行 `gh auth login --hostname github.com` 得到
`gh: managed GitHub CLI is unavailable (/opt/gh/bin/gh); install the bundled gh binary first`。

根因（代码证据）：

1. **入口受管、实体无主**：build317（T49）把 `gh-wrapper.sh` 与 `gh-proxy.mjs` 纳入受管资产
   （`app/src/main/assets/managed-runtime-inputs.json`、`tools/asset-deployment.json`），但包装脚本依赖的真实二进制
   `/opt/gh/bin/gh` **从未进入任何交付路径**：没有打包、没有固定输入、没有安装脚本。旧机能用，只是因为用户手工把官方
   gitHub CLI v2.103.3 装进了 `/opt/gh`（38,142,112 B，SHA-256 `a82a52e1…`，与官方 linux-arm64 归档成员逐字节一致）。
2. **错误文案与事实不符**：`gh-wrapper.sh` 原第 19 行声称 "install the bundled gh binary first"，但 APK 内没有这个字节。
3. **工具目录没有跨重建契约**：受管更新只替换 `ManagedRuntimeLayout.paths()`（不碰 `/opt`）；整树重建把整个
   `files/linux` 移走再解压，`/opt` 仅因“不在 `MaintenanceDataSnapshot.SYSTEM` 集合里”被**隐式**当用户数据复制，
   没有测试、没有文档，且本机 `/opt` 已达 3.5 GB / 48,294 条目，逼近 `BackupLimits.ENTRIES = 100_000` 的硬上限。
   因此任何**从未装过 gh 的环境**（全新安装、测试包、恢复重建）都会稳定复现该报错。

结论：这是**缺陷**，不是“基础环境变更就该清空用户工具”的设计。修复方向是补齐“gh 本应纳入受管工具”的供给链，
并把 `/opt` 的重建语义写成明文契约。

## 2. 修复（A + B + C）

### B（主）：把 gh 二进制纳入受管资产

- 新增固定输入 `app/src/main/assets/gh-cli.tar.gz` = 官方 `gh_2.103.3_linux_arm64.tar.gz`
  （13,661,485 B，SHA-256 `ee32df23…`）；锁为 [`tools/gh-cli/packages.lock.json`](../../tools/gh-cli/packages.lock.json)，
  同时记录成员 `gh_2.103.3_linux_arm64/bin/gh`（38,142,112 B / `a82a52e1…`）与 MIT 许可摘要。
- 生成器 [`tools/prepare-gh-cli.py`](../../tools/prepare-gh-cli.py)：只从固定 URL 下载、校验归档摘要、只取固定成员、写出许可全文
  `app/src/main/assets/licenses/gh-MIT.txt`；`--check` 校验已还原字节。
- 受管安装项：`managed-runtime-inputs.json` 新增
  `{"asset":"gh-cli.tar.gz","target":"opt/gh/bin/gh","executable":true,"extract":{member,sha256}}`；
  `RuntimeTools` 在安装时用 `TarGzipExtractor` 只提取该成员、二次校验 SHA-256、原子发布并设 0755；
  `ManagedRuntimeLayout.paths()` 收编 `opt/gh/bin/gh`，整树重建时按受管注入而不是用户数据恢复。
- 失败全部 fail-closed：成员缺失/摘要不符/发布失败都不安装任何字节。

### A（兜底）：包装脚本自举

`app/src/main/assets/gh-wrapper.sh` 在默认路径 `/opt/gh/bin/gh` 缺失/不可执行/大小不符时：

- 只从固定 URL（`https://github.com/cli/cli/releases/download/v2.103.3/gh_2.103.3_linux_arm64.tar.gz`）下载；
- 校验归档固定 SHA-256 → 只解出 `gh_2.103.3_linux_arm64/bin/gh` → 再校验二进制固定 SHA-256 与字节数；
- 通过后 `install -m 0755` 到临时文件再原子 rename；任一步失败都**不安装、不执行**，并打印可复制的恢复命令；
- 自定义 `DSHA_GH_BIN` 路径不会被自动写入；`DSHA_GH_BOOTSTRAP=0` 可关闭自举；并发首个调用用锁目录串行化。
- 删除误导性的 “install the bundled gh binary first”，改为真实状态 + 固定版本/摘要的手工命令。

### C（契约）：环境重建目录归属

- 新增纯逻辑 [`util/MaintenanceToolPaths`](../../app/src/main/java/com/deepseekharness/app/util/MaintenanceToolPaths.java)：
  `SYSTEM_ROOTS`（与历史集合逐项一致）、`USER_TOOL_ROOTS = {opt}`、`managed()` 单点判定与 `classify()`；
  `MaintenanceDataSnapshot` 改为使用该单点，不再持有私有隐式集合。
- `rebuild` 前增加**有界预检**：只统计 `/opt`、不跟随链接；条目超过 `BackupLimits.ENTRIES`（100,000）时在移动旧树前
  抛出“用户工具目录超过环境重建快照上限”，大于 1 GiB 时在维护进度里提示复制成本。
- 文档：`docs/runtime-data-plugin-architecture.md` §1.3 写明两条路径的替换范围、`/opt` 保留与 `/usr/local/bin` 丢失、
  本机 3.5 GB / 48,294 条目实测与 10 万条上限；`docs/fixed-build-inputs.md` 更新为 12 项。

## 4. 手工恢复命令（0.2.2 环境，包装脚本已装但二进制缺失时）

```sh
curl -fsSLO --proto '=https' https://github.com/cli/cli/releases/download/v2.103.3/gh_2.103.3_linux_arm64.tar.gz
echo "ee32df2323c8847f5fac6cb6b4b69ca75828e9329a8f22f677021f7b3306ce63  gh_2.103.3_linux_arm64.tar.gz" | sha256sum -c -
tar -xzf gh_2.103.3_linux_arm64.tar.gz gh_2.103.3_linux_arm64/bin/gh
install -D -m 0755 gh_2.103.3_linux_arm64/bin/gh /opt/gh/bin/gh
gh --version   # gh version 2.103.3
```

- 固定摘要与官方 `gh_2.103.3_checksums.txt` 一致；解出的 `bin/gh` 与用户旧机 `/opt/gh/bin/gh` 逐字节相同（`a82a52e1…`）。
- 也可设 `DSHA_GH_BIN` 指向已有 gh（不会写入自定义路径）；`DSHA_GH_BOOTSTRAP=0` 关闭自动自举。
