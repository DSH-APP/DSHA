# DSHA 0.2.1-rc.5-20261109.2300-dsh0.2.2-rc.1 / build350

- 仮想画面のウィンドウ証跡の最小公開とマルチウィンドウ時の実行可能なヒント（T98、`33ceab2c7`）：`see` の `FRAME_NOT_READY` の細分化と tree / node / editor / anchor の「ウィンドウ利用不可」応答は、アクセシビリティでウィンドウを読める場合に最小の読み取り専用ウィンドウ証跡（`util/VirtualScreenWindowEvidence`）を添える：アプリ / システム / 入力メソッドのウィンドウ数、`focusedWindowId` / `activeWindowId`、`windowAmbiguous`、ウィンドウが一意な場合のみ対象ウィンドウの displayId / id / type / layer / bounds / focused / active / タイトル / パッケージ。タイトルは制御文字を除去し空白を折り畳んで 64 コードポイントに切り詰め、パッケージはパッケージ名形式を検証した場合のみ保持し、それ以外の不適格値は省略する。ノード本文・コントロール内容・スクリーンショット・完全なウィンドウ一覧は含まない。`NO_UNIQUE_APPLICATION_WINDOW` は件数で二つの原因を区別する：アプリウィンドウが複数並ぶ（分割画面 / フローティングウィンドウ）→ `reason=VSCREEN_WINDOW_AMBIGUOUS`、`nextAction=ASK_USER_TO_CLOSE_SPLIT_SCREEN`；システム / 入力メソッドのウィンドウのみでアプリウィンドウがない → `reason=VSCREEN_NO_WINDOW`、`nextAction=LAUNCH_APP_FIRST`。証跡は失敗と次の一手の説明にのみ使われ、**認可・ウィンドウ選択・再試行には一切関与しない**：セマンティック経路は引き続き `VirtualScreenWindowPolicy.selectDetailed` の唯一の結果だけを認め、アンカー経路は元の観察が持つ windowId だけを認める（同じ id の重複は従来どおり `ANCHOR_WINDOW_AMBIGUOUS` で拒否）。「マルチウィンドウ」を理由に別ウィンドウへ自動で切り替えることはない。
- 仮想画面のセンシティブ画面の段階とハンドオフ（T119、`dc6f9642e` / `c3a4e3c30` / `241e06159`）：新規 `util/SensitiveScreenClassifier` と `util/SensitiveScreenPolicy`（純粋ロジック）を追加し、6.1 のパスワードフォーカス強制ガードに加えて画面全体を保守的に分類する（パスワード / ワンタイムコード / 決済 / システムセキュリティ / センシティブだがツリーを読めない `SECURE_UNKNOWN`）。既定は全カテゴリ `ASK`。カテゴリごとに `HANDOFF` を設定でき、入力の配信前にアシスタントを一時停止し、進行中の要求を取り消して観察を破棄し、`ok:false` / `state=NOT_SENT` / `error=SENSITIVE_SCREEN_HANDOFF` / `sensitivity=<カテゴリ>` / `readOnly:true` / `retryable:false` / `nextAction=HANDOFF_TO_USER` を返す。ユーザーの再開後は必ず `see` し直し、自動で再実行しない。`OFF` は画面全体の段階付けだけを無効化し、通常の確認ポリシーへ戻す。パスワード文字列の読み書きは入力層の強制ブロックのままで、どの段階や確認でも解除されない。`ALLOW_ALL` とアプリ単位の `ALLOW` は通常確認を省くだけで、センシティブカテゴリの `ASK` を飛ばせない。センシティブ確認は 1 回限りの認可で、**「このターンはこのアプリを許可」の 5 回メモリには書き込まない**（通常アプリは従来どおり 5 回ごとに再確認）。設定 → デバイス機能の許可 → 画面認識に「センシティブ画面のハンドオフ」の独立行を追加し、カテゴリごとの「確認 / ハンドオフ」と、強制ハンドオフと信頼アプリの 2 つの完全一致パッケージ名リスト（既定は空、各最大 64、相互排他、破損時は ASK に戻る）を管理できる。画面認可の `policyRevision` は `screen_confirmation_v1` と `sensitive_screen_v1` の改訂番号を合成し、どちらの保存でも古い確認と進行中の要求を無効化し、プロセス内では単調な下限を保つ。入力を注入するエンドポイントは確認後・配信前に再分類し、読めない場合は `SENSITIVE_SCREEN_UNVERIFIED`、カテゴリが変わった場合は `SENSITIVE_SCREEN_CHANGED` を返し、どちらも未送信で再観察が必要。
