# DSHA 0.2.1-rc.5-20261110.0700-dsh0.2.2-rc.1 / build352

- Исправление регистрации плагинов при первом запуске после переустановки поверх (T135, `092b8848d`): бюджет регистрации теперь ступенчатый по идентичности управляемых активов — 90 с для обычного запуска и 240 с для первого. Хост читает `runtimeId` из `runtime-descriptor`, guest читает `managed-assets-v2`; после успешной регистрации атомарно записывается `register-managed-asset-id`, а прерванная по таймауту попытка ничего не записывает, поэтому следующий запуск снова получает расширенный бюджет. Скрипт регистрации получает `--clear-stale-profile-lock` (обходит `operation_lock` и удаляет только блокировки подтверждённо завершившихся держателей), а хост после таймаута регистрации один раз выполняет очистку с коротким бюджетом 10 с; `plugin-manager list` сообщает `PLUGIN_PROFILE_LOCK_STALE` (можно повторить) для мёртвых держателей вместо расплывчатого «конфигурация изменяется». `StartupRecoveryState` получает `Kind.REGISTER`, распознающий `BUILTIN_REGISTER_TIMEOUT` / `EXIT_` / `RECEIPT_MISSING` и `PLUGIN_PROFILE_LOCK_TIMEOUT` / `STALE`; заголовки и описания говорят «регистрация плагина истекла / не завершена / блокировка ждёт подтверждения — можно сразу повторить», а `StartupText` оставляет только действенный вывод, убирая сырые `exit=` / `timedOut=` / guest JSON (исходный текст остаётся в истории запусков и журналах). Поэтапный хронометраж хоста: команда регистрации проходит через построчный callback Runner, сообщение об ошибке дополняется `hostElapsedMs` и последним этапом `REGISTER_TIMING`, а при превышении гостем настенных часов хоста явно выставляется `GUEST_TIMING_MISMATCH`. Без повторной установки оверлея при первом запуске: `RuntimeTools` пишет межпроцессную отметку завершения `.runtime-tools-prepared` (относительный набор управляемых файлов + `RuntimeAssetStamp`), которая переиспользуется только при полном совпадении идентичности APK, зарегистрированного descriptor и отметки метаданных, иначе выполняется полная подготовка. Регистрация включена в проверку готовности обслуживания: статическая проверка `RuntimeTrial` в update становится `register=true`, `requireCompleted` + `BUILTIN_REGISTER_OK`, регистрация завершается до пробного запуска Web, а сбой откатывается вместе с транзакцией. Добавлены модульные тесты `RegisterBudget` / `GuestTimingEvidence` / `RuntimePreparedProof`, а также случаи бюджета регистрации, доказательства хронометража, очистки блокировки по таймауту, классификации `REGISTER` и свёртывания `StartupText`; в `tools/` добавлены тесты состояния / перехвата / очистки блокировок, маркера идентичности и списка устаревших блокировок. **479409 ms не приписываются ни одному отдельному подэтапу** — в диагностику попадают только времена хоста и guest и последний этап, а первый запуск после переустановки по-прежнему требует проверки на устройстве.
- Канал наблюдения за страницей внешнего устройства (T134, `24130f244`): новый `/app/extdev/watch` (`mode=events` / `window`) непрерывно сэмплирует буфер events цели в одном выделенном сеансе ADB, поэтому проверка больше не перезапускает сервер; он возвращает пакет / Activity на переднем плане, digest, привязанный к generation цели, `sequence` и `settle`, а курсор `since` связывает вызовы в «ожидание смены страницы». `operate` поддерживает `observe=1`: если действие отправлено (не UNKNOWN), прикладывается наблюдение из 4 сэмплов; сбой наблюдения пишет только `observationUnavailable` и никогда не переписывает статус действия, а семантика `NOT_SENT` / `POLICY_BLOCKED` / `UNKNOWN` не меняется. Чистая логика `ExternalFocusEvents` / `ExternalWatchPolicy` / `ExternalRateLimit` вынесена с модульными тестами; сэмплирование остаётся на белом списке команд только для чтения (без `logcat -t`: на устройстве он сначала обрезает сырой хвост, а затем фильтрует, давая пустой результат). Измерение на устройстве (OnePlus PJD110 / Android 16): обнаружение по сэмплированию logcat events p50 123 ms, `dumpsys window` 128 ms, `screencap` 922 ms; первый кадр h264 из `screenrecord` — 37–43 ms, но требует декодирования / разницы кадров, оставлен на Phase C. Обновлены `/app/help` (китайский и английский), индекс документации и `tools/java-format-files.json`, пересчитан descriptor среды выполнения (`HttpShellService` / `BridgeRoutes` — входы launcher). **`/app/extdev/watch` — новый эндпоинт без приёмки на устройстве на уровне эндпоинта; нужна пофакторная приёмка тестовым пакетом на PJD110.**
- Отчёт о поиске корневой причины сбоя первого запуска после переустановки build351 (T133, `bf59e8864`, только документация): классифицирован в основном как ③ отсутствие механизма (фиксированный бюджет регистрации 90 с, без ступеней / продления, без очистки блокировки по таймауту), усугублённое ① цепочкой проектирования (повторная установка управляемого оверлея при первом запуске, остаточная блокировка профиля, повторно сообщаемая страницей восстановления) и ② недостаточной семантикой (`BUILTIN_REGISTER_TIMEOUT` не классифицируется / попадает в `STARTUP_FAILED`, сырые `exit=` / JSON показываются напрямую). Доказательства — таймлайн страниц восстановления / обслуживания и локальная база нормального запуска build351 (register 870 ms, stamp 65 ms, 101 элемент); зафиксировано, что 479409 ms guest не согласуются с бюджетом хоста 90 с, и это отнесено к пробелам, требующим полевых доказательств, **без вывода подэтапа из этого числа**. Отчёт даёт указанное минимальное исправление и чек-лист воспроизведения / сбора доказательств тестовым пакетом и не меняет production-код.
