# DSHA 0.2.1-rc.5-20261109.2300-dsh0.2.2-rc.1 / build350

- Минимальное свидетельство окон и подсказка о многозадачности для виртуального экрана (T98, `33ceab2c7`): детализированные ответы `FRAME_NOT_READY` от `see` и ответы «окно недоступно» от tree / node / editor / anchor теперь содержат минимальный снимок окон только для чтения, когда специальные возможности могут читать окна (`util/VirtualScreenWindowEvidence`): счётчики окон приложений / системы / методов ввода, `focusedWindowId` / `activeWindowId`, `windowAmbiguous`, а при единственном доступном окне — ещё displayId / id / type / layer / bounds / focused / active / заголовок / пакет целевого окна. Из заголовков удаляются управляющие символы, пробелы сворачиваются, заголовок обрезается до 64 кодовых точек; пакеты сохраняются только после проверки формата имени пакета, остальные недопустимые значения опускаются. В снимке нет текста узлов, содержимого элементов управления, скриншотов или полного списка окон. `NO_UNIQUE_APPLICATION_WINDOW` теперь по счётчикам различает две причины: несколько окон приложений рядом (разделённый экран / плавающее окно) → `reason=VSCREEN_WINDOW_AMBIGUOUS`, `nextAction=ASK_USER_TO_CLOSE_SPLIT_SCREEN`; только системные окна и окна методов ввода без окон приложений → `reason=VSCREEN_NO_WINDOW`, `nextAction=LAUNCH_APP_FIRST`. Свидетельство только объясняет сбой и следующий шаг и **никогда не участвует в авторизации, выборе окна или повторах**: семантический путь по-прежнему принимает только единственный результат `VirtualScreenWindowPolicy.selectDetailed`, а путь якоря — только windowId из исходного наблюдения (повтор того же id по-прежнему отклоняется как `ANCHOR_WINDOW_AMBIGUOUS`); при «нескольких окнах» другое окно автоматически не выбирается.
- Уровни чувствительных экранов и передача управления для виртуального экрана (T119, `dc6f9642e` / `c3a4e3c30` / `241e06159`): новые `util/SensitiveScreenClassifier` и `util/SensitiveScreenPolicy` (чистая логика) добавляют консервативную классификацию всего экрана поверх жёсткой защиты фокуса пароля из 6.1 (пароль / одноразовый код / платёж / системная безопасность / чувствительно, но дерево не читается `SECURE_UNKNOWN`), по умолчанию для всех категорий `ASK`; для каждой категории можно задать `HANDOFF` — перед отправкой любого ввода приостановить помощника, отозвать текущие запросы и отбросить наблюдения, вернув `ok:false` / `state=NOT_SENT` / `error=SENSITIVE_SCREEN_HANDOFF` / `sensitivity=<категория>` / `readOnly:true` / `retryable:false` / `nextAction=HANDOFF_TO_USER`; после возобновления помощник обязан снова выполнить `see` и никогда не повторяет автоматически. `OFF` лишь отключает уровни всего экрана и возвращает обычную политику подтверждений. Чтение и запись парольного текста по-прежнему жёстко блокируются на уровне ввода и не снимаются ни одним уровнем или подтверждением. `ALLOW_ALL` и правило `ALLOW` для приложения пропускают только обычные подтверждения и не могут обойти чувствительный `ASK`; чувствительное подтверждение одноразовое и **не записывается в память «разрешить это приложение на этот ход» на 5 раз** (обычные приложения по-прежнему переспрашивают каждые 5 раз). В «Настройки → Разрешения устройства → Наблюдение экрана» добавлена отдельная строка «Передача чувствительных экранов» с выбором «спросить / передать» по категориям и двумя точными списками пакетов (принудительная передача и доверенные приложения; по умолчанию пустые, до 64 в каждом, взаимоисключающие, повреждённые данные возвращаются к ASK). `policyRevision` экрана объединяет ревизии `screen_confirmation_v1` и `sensitive_screen_v1`, поэтому любое сохранение аннулирует старые подтверждения и текущие запросы, а в процессе держится монотонный нижний предел; конечные точки, отправляющие ввод, повторно классифицируют после подтверждения и перед отправкой — нечитаемый экран возвращает `SENSITIVE_SCREEN_UNVERIFIED`, изменённая категория — `SENSITIVE_SCREEN_CHANGED`, оба случая не отправлены и требуют нового наблюдения.
- Исправления островка (капсулы уведомлений) (PR #12, `ccd4b81d7`, уже в main): в развёрнутом виде остаётся один индикатор хода (subText уведомления), тело больше не повторяет «ход N», а во время работы не пишется секундное значение, поэтому подпись содержимого стабильна и перестроения по пульсу больше не перехватывают нажатия кнопок вариантов; сбои фонового ответа должны быть видны — HTTP-код не 200, пустая отправка, истёкшие варианты или недействительный вход показывают Toast (с HTTP-статусом и кодом ошибки сервера, например `HTTP 409 NO_WAITING`) и предлагают открыть чат, а в журнал приложения пишется `TASK_ANSWER_REJECTED <status> <body>`; при открытии чата из уведомления проверяется наличие реальной строки вариантов (`Mbwy4a_optionRow`) — контейнер `Mbwy4a_options` отрисовывается на каждой карточке и давал бы всегда истинный результат; при наличии вариантов фокус не перехватывается, клавиатура остаётся скрытой, чтобы нижняя кнопка «Отправить» не выходила за пределы экрана. В `docs/island-status.md` добавлена таблица статусов проверки платформ: нативный Android 16, 16 QPR1+, HyperOS, ColorOS 16 и OriginOS 6/7 размечены построчно (поддержка по ветке платформы / поддержка в коде без проверки на устройстве / наблюдение участника на устройстве без коммита / открытые данные без проверки на устройстве / ожидаемая поддержка без записи о запуске), а OriginOS 7 (Android 17) явно указан без записи о запуске на устройстве в репозитории.
