# DSHA 0.2.1-rc.5-20261106.2228-dsh0.2.2-rc.1 / build334

- P0 덮어쓰기 업데이트 수정(T91, `a70232fc`): build333 실기기 덮어쓰기 업데이트 후 proroot 런처가 시험 guest 종료 후 늦게 종료되거나 남아 있는 경우가 있었다(OnePlus PJD110 / Android 16 / WebView 156 실측, 백그라운드에 다른 Web이 없어도 재현). `RuntimeTrial` 마무리 단계가 "런처 객체가 아직 살아 있음"을 시험 실패 `TRIAL_PROCESS_UNCONFIRMED`로 오판해 런타임 업데이트 트랜잭션이 반커밋(`files-committed` / `settings-committed`) 상태로 남았고, 시작이 유지보수 장벽에 막혔으며 재시작해도 해결되지 않았다. 이제 trial 마무리는 이 기록의 guest 종료 증거만으로 확인하고, 런처 잔류는 결론을 바꾸지 않는다. `RuntimeTrial`은 이번에 보유한 `Process` 핸들에 대해 한 번만 유계 정리하고, 시간 초과나 실패 시에는 `TRIAL_LAUNCHER_RETENTION` 진단만 기록한다. `launched`이지만 `.dsha-web.pid` / `.stale` 증거가 없는 기록은 `TrialRecovery`가 해당 기록 id에서 유도한 시험 profile에 그런 프로세스가 없음을 플랫폼에 확인하도록 요구한다(동일 UID, 두 번 일치하는 출생 신원). 여전히 존재하거나 읽을 수 없거나 신원이 바뀌면 계속 fail-closed로 유지하며, 스스로 치유할 수 없는 증거 결손을 무조건 남기지 않는다.
- 유지보수 실패 진단과 오래된 실패 정리: 유지보수 작업 시작/실패가 내보낼 수 있는 작업 기록(`MAINTENANCE_TASK_START` / `MAINTENANCE_TASK_FAILED`)을 쓰고, 실패 상태에서도 비상 DSH, 유지보수 기록, 내보낼 수 있는 읽기용 사본, "제한된 메인 UI로 들어가기"를 계속 누를 수 있게 한다. 외부 복구가 끝나고 환경이 실행 가능하며 진행 중이거나 복구 대기 중인 유지보수가 없으면, 페이지는 오래된 실패 스냅샷(`RuntimeUpgradeState.clearStaleFailure`)을 버리고 "이전 런타임 업데이트 대기"라는 표준 상태로 돌아가 업데이트 진입점을 제공하며, 사용자에게 다시 재시도를 누르게 하지 않는다. 시작 기록은 "인증 링크는 받았지만 최종 ready/failed를 쓰지 않은" 상태를 "준비 완료 · 진입 대기"로 표시하고 "중단 · 결과 없음"을 표시하지 않는다.
- 덮어쓰기 업데이트에서 이전 버전 은퇴(I10): 설치된 APK 신원과 기록된 세션 신원이 다를 때만 유지보수/강제 중지 경로에서 기록된 출생 신원(boot, PID, 출생 시각, 명령줄, UID, 세대/인스턴스/nonce)을 두 번 검증한 뒤, 먼저 기록의 guest를 종료하고 다음으로 그에 해당하는 이전 proot 런처를 종료한다(SIGTERM → 짧은 대기 → 재확인 → SIGKILL). guest 종료가 확인되지 않으면 런처를 건드리지 않고, 검증 실패/읽을 수 없음/PID 재사용/타인 UID/두 관측 사이의 변화가 있으면 아무 신호도 보내지 않고 원래 환경을 유지한다. 일반 중지, 현재 인스턴스, 터미널, 가상 화면, 격리 시험 경로는 그대로다(I9). 강제 중지 대화상자는 "이전 Web을 포기하고 강제 종료"와 guest → 이전 런처 순서를 명시한다.
