## 2. 问题与根因

用户反馈（旧版）：正式实例停在「尚未启动」，「恢复中断维护」（`DSHA_RECOVER_MAINTENANCE_V1`）连续 3 次停在「正在停止 Web，等待运行队列完成…」并报 `PLUGIN_JOURNAL_ID`；重建 Web Profile 被 `REPAIR_RECOVER_PENDING_FIRST` 拒绝；启动检查中 `user-data-v5/dsh` 为 MISSING（未迁移时回退旧数据根，属正常）。

源码核对结论：

- `PluginInstallJournals.pending` / `archiveCompleted` 与 `plugin-transactions.py` 的 `pending` / `archive_terminal` 只跳过 `completed` 与 `.completed-proof-v1.json`，其余非 UUID 名字直接失败。
- 完成证明本身由 `BackupFileSystem.atomic` 写在 `plugin-install-operations/` 内；崩溃会按设计留下 `.previous`、`.previous-retained-*`、`.tmp-*`、`.restore-*` 兄弟文件，之后扫描永久失败。
- `PluginInstallJournals.blocked` 把不可读当作待恢复，恢复入口又依赖同一扫描，`RecoveryRepairBroker` 因此拒绝其他修复，形成死循环。
- 未取得该用户目录的实际列表，无法确认其残留具体是哪一类；手动放入或从备份带入的非 UUID 条目会产生同样现象，本版对两者都不再阻塞。
