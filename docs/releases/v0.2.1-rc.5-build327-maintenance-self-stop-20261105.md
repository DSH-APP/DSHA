# build327 变更与已知问题：维护动作自行完成“完全停止”（2026-11-05）

> **状态：截至本记录提交时，未做真机验证。** 本文给出宿主阶段（JVM 单测 + 契约检查）的实跑结果
> 与真机核对清单；真机结论必须等用户按第六节逐项回复后补写，**不预写「已通过」**。
> 持久化契约见[覆盖安装、运行时维护与内置插件依赖契约](../overwrite-upgrade-and-maintenance.md)（I1–I9）。

## 一、用户报告

- 原话：「还是会卡住，覆盖更新不会自动彻底强制停止 web，哪怕已经有相关的设计」。
- 补充路径（用户确认）：「进入覆盖页（维护页），会提示要求完全停止。实际操作流程上需要**先进入受限主界面，然后点『停止』，然后再回来点『更新运行时』**才能完成运行环境维护。」
- 即：维护页自己**只要求**停止，不执行停止；用户被迫走「受限主界面 → 停止 → 回维护页 → 更新」三步。

## 二、根因（可核对代码路径）

1. 维护页确认按钮 → [`RuntimeMaintenanceStarter.showRetryDialog`](../../app/src/main/java/com/deepseekharness/app/ui/RuntimeMaintenanceStarter.java) → `BackupTask.updateEnvironment()`。
2. [`BackupTask`](../../app/src/main/java/com/deepseekharness/app/core/BackupTask.java) 以 `stopWeb=true` 启动任务，worker 调 [`MaintenanceCoordinator.exclusive`](../../app/src/main/java/com/deepseekharness/app/core/MaintenanceCoordinator.java) → `MaintenanceGate.exclusive` → `ports.stopWeb()`。
3. 旧实现的 `MaintenanceCoordinator.stopWeb` **只**调用 `controller.stopWeb(...)`（普通停止：哨兵 + PID 文件 + 出生身份核验），最多等 45 秒；未确认退出时直接抛 `controller.lastStopError()`（`PENDING_EXIT` 文案：「已请求停止，Web 尚未退出；稍后可重试，未强杀容器启动器」）或超时文案。**它从不调用既有的身份核验强制停止。**
4. 既有的 `HarnessController.prepareForceStop()` / `forceStop()` 只接在 [`LaunchFragment.offerForceStop`](../../app/src/main/java/com/deepseekharness/app/ui/LaunchFragment.java) 的手动停止失败对话框上。用户为了完成维护，只能先进入受限主界面点停止（那里有强制结束入口），再回维护页点更新——正是用户描述的三步绕道。
5. `hasUnresolvedWebSession()` 拦截 `shouldAutoStart` 是**正确**的安全门禁（契约 I4），只决定“不自动开始”，不是本次卡住的原因；本次修的是用户手点之后维护动作自己不执行完全停止。

## 三、本版改动

1. **维护前停止编排**：新增 [`MaintenancePreStop`](../../app/src/main/java/com/deepseekharness/app/core/MaintenancePreStop.java)（`core/`，纯顺序逻辑）：
   - 请求普通停止（复用既有哨兵 + PID 文件 + 出生身份核验）；
   - 等待 guest 与启动器退出证明；
   - 普通停止未确认时，**只升级一次** `prepareForceStop()` 身份核验候选 + `forceStop`；
   - 仍无法确认 → 抛出含「原运行环境未改动 / 点重试更新运行时」的失败文案，不静默继续。
2. **接线**：[`MaintenanceCoordinator`](../../app/src/main/java/com/deepseekharness/app/core/MaintenanceCoordinator.java) 新增 `exclusiveUserConfirmed` 与 `stopWeb(controller, allowForceStop)`；[`BackupTask`](../../app/src/main/java/com/deepseekharness/app/core/BackupTask.java) 的开始方法增加 `allowForceStop`。**只有用户在确认对话框确认之后**的更新 / 重建 / 恢复 / 回退 / 隔离等动作才允许强制；自动开始（`updateEnvironment()`）与闲时清理仍走不带强制的 `exclusive`。
3. **覆盖安装后的残留进程**：`StoredWebSession.Record` 自始就带加密的 `proof`（boot、代次、实例、nonce、guest 与 launcher 的 PID + 出生时间 + 命令行），**不需要改记录格式或迁移**；老记录按「无法核验」降级，不杀。新增 [`WebProofStop`](../../app/src/main/java/com/deepseekharness/app/util/WebProofStop.java)：只在两次完整核验一致时 SIGTERM，允许强制时再次复核后 SIGKILL；PID 复用、出生时间/命令行变化、记录不可读都**不发送任何信号**，启动器永不被结束。[`WebLifecycleController.prepareForceStop`](../../app/src/main/java/com/deepseekharness/app/core/WebLifecycleController.java) 在 PID/身份文件不可用时回退到这份候选。
4. **诊断**：`WebStopDiagnostic` 新增 `RECORDED_SESSION_UNCONFIRMED`，`WebStopText` 给出「已保存的 Web 出生身份与当前进程不符或无法读取，未发送任何信号」。

## 五、本版不改的东西

- 不改 `EnvironmentAccess.requiresMaintenanceBeforeStart` / `EnvironmentIdentity.shouldBlockRuntimeStart` / `WebLifecycleController` 启动准入。
- 不改任何固定构建输入（`offline-rootfs.bin`、`dsh-runtime.bin`、`ubuntu-tools.bin` 等）；只重算 APK 内 `runtime-descriptor.json`（宿主 launcher 源变化是补丁级契约变化）。
- 不按端口反查、不按名称/进程组终止；强制停止只结束 guest，proot/proroot 启动器永不结束。
- 不把强制停止用于自动路径。

## 六、真机验收清单（待用户确认）

- **S1（主场景）**：build326 → build327 覆盖安装（同包名、同签名、非调试），覆盖前**不手动停止** DSH / Web。
  - 首次启动停在整屏「运行环境维护」页；
  - 点「更新运行时」→ 安全确认对话框 →**不需要先进受限主界面点停止**；进度面板出现并在 stop 阶段自行停止旧 Web；
  - 完成后主操作变为「进入主界面」，Web 正常加载，插件加载，`runtimeId` 变成 build327 的候选。
- **S2（停止失败可见）**：若 stop 阶段失败，页面必须给出原因（含「原运行环境未改动 / 重试更新运行时」），且用户可再次手点重试；不得静默停在进度或要求绕道。
- **S3（冷覆盖对照）**：先正常停止 DSH 与终端再覆盖安装，维护自动开始一次并成功。
- 回执字段：上一版 → 本版、安装方式、旧 Web 是否存活、看到的页面、自动开始是否被拦、手点后是否成功、Web / 插件结果、`runtimeId` 前后值。设备截图与日志不进入仓库。

## 八、已知问题 / 本版未覆盖

- **未真机验证**：本文结论只到宿主阶段；真机路径（尤其覆盖安装后旧 Web 存活分支）等用户核对。
- 强制停止仍受 ROM 的 hidepid / 权限限制：无法核验或无法确认退出时保留原环境并给出文案，不绕过。
- 若 guest 已退出但容器启动器迟迟不退，维护会按既有屏障失败并提示重试；不会结束启动器。
- 维护页的“三步绕道”反馈来自 build326 真机；本版在 build327 测试包上需重新确认 S1/S2。
