# DSHA rc2 旧 Web 身份与应急请求修复

2026-09-27 本地修订。保留 DSHA `0.1.7-rc2` / 147、DSH `0.1.7-rc.2`、Ubuntu 10、E7E3 签名及两版常规文件名。此记录在[APK 体积修订](v0.1.7-rc2-apk-size.md)基础上补充本轮证据。

## 输入与实际根因

用户提供的 vivo V2463A / Android 16 日志在 00:04:35 和 00:06:36 均于「停止旧 Web 进程」失败：`WEB_PROCESS_INSPECTION_UNCONFIRMED:DENIED`。应急 DSH 于 00:05:51 达到 `RECOVERY_READY`，本次端口为 33471。因此正式 Web 的停止屏障失败与应急网页中的对话错误是两件事；日志未证明二者共用过期鉴权码。

当前代码对旧 PID 执行 `kill(pid, 0)`；当 Android 16 的进程可见性策略遮住了被复用编号的 UID、内核又返回 `EPERM` 时，会返回 `DENIED`，每次重试都读回同一条旧记录。修复只对**主 Web、有效的旧 PID+出生时刻记录、UID 仍不可读、明确的内核 signal-0 权限拒绝且连续两次结果一致**隔离记录。不会向该编号发结束信号。单纯 `/proc` 内容拒读、记录缺失或损坏、已核实的本应用 UID、signal-0 成功但身份不可读，以及隔离试运行仍保持停止屏障；没有清理用户数据。`EPERM` 的一般含义是无权给该目标发送信号，并非单独的 UID 证明；本分支依赖主 Web 由本应用 UID/运行域启动的约束。[Linux kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html)

应急截图中的 `REQUEST_EXTENSION` 则来自 rc2 的模型请求扩展准备：应急插件 `package.json` 原来写入包名却没有版本，而官方活动插件清单在模型 HTTP 请求前要求有效 `name` 和 `version`。为新应急会话补上固定插件版本 `0.1.0`；不改正式插件。宿主测试用真实 rc2 Profile、真实插件清单服务与浏览器创建会话，在无外部模型请求时调用官方扩展 `prepare()` 并读回应急插件版本。原生应急页和浏览器页也明确展示本次启动缺少模型凭据时的操作入口；缺凭据不能被误报成旧 Web 身份错误。

Low 真机先经过同基础受管更新及隔离网页试运行，正式 Web 进入 Gecko 页面。最后一次收紧进程判据后，同签覆盖的 Low 再次完成维护，正式 DSH 达到 READY。然后启动独立应急 DSH，到达 READY，进入应急 Web；无模型密钥时，新提示和返回原生页入口均实际可见，正常停止后应急现场保留。最后覆盖 Standard，正式 Web 再次到达 READY 并进入系统 WebView 页面。该设备的正式页面同时显示既有的「无法创建默认工作区，请通过『选择工作区』选择文件夹」，因此这次不能把页面出现当作工作区/模型发送已通过。

vivo V2463A 不在本机连接设备中，不能把宿主夹具及另一台小米的通过写成 vivo 已复现通过。应急用户会话未在报告设备上获得模型请求成功证据；其它供应商模型、久置后的真实重试、Android 6/7、真实 16 KiB 内核仍未覆盖。
