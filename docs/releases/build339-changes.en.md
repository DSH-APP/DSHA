# DSHA 0.2.1-rc.5-20261108.0300-dsh0.2.2-rc.1 / build339

- Second confirmation when switching the screen-recognition setting (T113, `29c5028b`): when the user chooses physical or virtual under Settings → Device capability grants → Screen recognition, a `DshaDialogBuilder` confirmation now explains the capture scope and that it can be revoked; the switch happens only after confirmation, and success, failure, pending-cleanup and repeated selection all get inline status and a toast. Confirmation is not skipped by the "allow all" confirmation mode. The new `ScreenModeFeedback` is the single source for the confirmation rule, mode names and result copy; repeated taps are ignored while switching; the Chinese/English confirmation dialog scrolls on a 320 dp short screen with 1.3× font.
- Smaller emergency-DSH startup page and single-layer confirmation flow (T92, `da0b9b71`): the first screen's explanation becomes one conclusion line + ⓘ; status and the start / enter / stop actions merge into one card; the temporary API key is collapsed by default, and diagnostics / logs / backup / return-to-recovery move under "More"; status and action results fade with UiMotion. The confirmation flow gains `RecoveryRepairSheet`: selection and preview switch inside the same dialog, Back goes up exactly one layer, repeated taps are disabled while a preview is generated, execute / reject stay inside the scrollable content (short screens and large fonts scroll), and no execute entry appears for an empty proposal ID; the emergency Web header becomes a single-line title + short action "Repair proposal" + reload icon + divider.
- Password-focus guard before assistant text writes on the virtual screen (T97 P1, `8b82e4f7`): the pure-ASCII fast path of `/app/vscreen/type` executed `input text` directly in the Core and bypassed the accessibility password checks. The new `VirtualScreenTextInputPolicy` hard-rejects password focus, allows safe focus, fails closed when a semantic channel exists but focus is unreadable, and keeps the documented ASCII capability with `passwordFocusChecked=false` when accessibility is not connected; the read-only `VirtualScreenPasswordProbe` re-checks the current display's single application window via ACTION_AUTHORITY and reads `FOCUS_INPUT`, returning `SCREEN_TARGET_CHANGED` without sending if the window changed. ASCII dispatch is pre-checked: password focus returns `PASSWORD_INPUT_UNAVAILABLE` (`state=NOT_SENT`, `nextAction=REPORT_TO_USER`), unreadable focus returns `PASSWORD_FOCUS_UNVERIFIED` (`retryable`, `SEE_AGAIN`); non-ASCII type and node `set_text` now also reject password nodes; the native panel keeps its independent lease and is unaffected. There is no "allow anyway".
- T97 CI test-seam fix (`d16b0c14`, test infrastructure): `VirtualScreenInput` gains an instance-level forced-available flag so test instances are no longer hijacked by the host's `/system/bin/input` probe (the GitHub runner lacks that file, which made the T97 unit tests fail); production instances never set the flag, a real missing command is still rejected, and `systemCommandExists` is not relaxed.
- Virtual-screen display-spec whitelist presets (T99, `c33f358d`): the default stays 1008×1792@320 (16:9 / 504×896 dp) and a new compatibility baseline compat-720 = 720×1600@320 (20:9 / 360×800 dp) is added; unknown / empty / over-budget specs fall back to the default and arbitrary sizes or dpi are not accepted. Manager creation and rotation now pass only a preset id and orientation to the Core, which resolves the whitelist and applies dpi, reading back preset / density / logical sizes; `VirtualScreenDisplaySettings` persists the choice and the virtual-screen page gains a "Display size" radio group that affects only the next creation or rotation rebuild, not the current frame identity or input gate. The observation budget stays 2 frames / 24 MiB, so two 1440×2560 frames (~28.1 MiB) are not whitelisted; compat-720 device validation is not done.
- Physical-screen action-as-observation and event-driven settle (T105, `c6a2ea84` / `c94df74d` / `00dd7a90`): `/app/ui` action endpoints accept an optional `observe=1` — after the action reaches `COMPLETED`, the same request settles (first accessibility event ≤800 ms, 250 ms quiet, 2.5 s total cap; cancellable and deadline-bounded, no busy polling) and re-reads the tree, returning new `treeId` / `nodeId`, the text tree and settle metadata in the receipt; coordinate actions still never return a screenshot and coordinate credentials still require a separate screenshot. Omitting the parameter keeps the old behaviour; an observation failure only writes `observationUnavailable` and never rewrites the action status; UNKNOWN is never replayed; credential-expiry rejections carry the current screen's new tree so callers can retry with fresh credentials. The built-in `dsh-computer-use-android` gains an optional `observe` on its seven action tools (omitted → the MCP server injects `observe=1`, `observe:false` disables it; only optional fields are added and strict argument validation is not relaxed). Consecutive `/app/sense/state` calls now default to a delta: more than one third changed, window / size / focus / source / truncation state changes, generation or target changes and `full=1` return a full snapshot, while no change returns `mode=same` with a single line; responses add `mode` / `deltaReason` / `previousSid` / `changedElements` with `format=v4-preview-3`. `k***` remains a reading-order position label, and actions still use one-shot `treeId` / `nodeId` leases. `/app/help` is updated in Chinese and English.
- Guidance for user plugins whose version no longer matches after a runtime upgrade (T93, `bebc01b4`, docs): APK / DSH overwrite updates do not rewrite the user profile's third-party plugin manifest or `node_modules`; the DSH compatibility pre-check skips incompatible bundles and disables matching entries by `engines.dsh` / `@deepseek-ai/dsh*` peer ranges (fail-safe; user plugins are not deleted or rewritten). Handling goes through plugin-management reinstall and exact-version exemptions in `compatibility.json`, never hand-editing the profile; the note also explains that repeated startup lines from multiple cordis entries of the same bundle are not duplicate module imports (StartupTrace additionally de-duplicates adjacent identical lines).
- Design evaluation of the two physical-screen observation paths (T107, `ee5adfde`, docs): recommends direction C (privileged mirrored reading plus evdev physical-input detection); user activity detection does not depend on frames, mirrored frames never issue coordinate / action credentials, and the lightweight A approach remains the unprivileged fallback marked `userActivity=UNKNOWN`; permissions default off, activate per task, are revocable and fail closed. This build only carries the evaluation: no product code, and no device validation of frame capture / evdev / channel permissions.
