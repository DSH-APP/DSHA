## 本轮修复

### DeepSeek Messages 的嵌套工具调用

Agent Team 与子代理投递会把用于展示的 `tool-call` 块保留在 `user` 消息或另一个工具的 `tool-result` 中。DSH alpha.2 的 DeepSeek Messages 序列化器只允许 assistant 消息包含真实工具调用，因此在普通运行或 compact 重放旧会话时会抛出：

```text
DeepSeek Messages cannot represent user/tool-result content tool-call
```

build 141 对锁定的 `@deepseek-ai/dsh-llm-deepseek` alpha.2 源码应用受管补丁，只把上述展示块投影为包含 `id`、`name` 和 `arguments` 的稳定文本。该投影不修改旧会话文件，也不把展示内容重新执行成工具调用。assistant 的真实 `tool_use`、调用 ID 与顺序，普通及失败的 `tool_result`，以及图片结果仍保持 DeepSeek Messages 的原协议结构；其它不支持的内容类型继续明确报错。

回归覆盖了截图中的 Agent Team 路径、compact、普通双工具、嵌套失败结果、图片结果和旧会话输入不变。`node tools/test-deepseek-messages-compat.mjs` 已通过。

### 系统插件与用户插件分层

- 签名系统插件由当前 APK 管理。备份不再归档其源码、旧实体或依赖，只在插件图 v2 中保存各 profile 的启用/禁用意图。
- 用户插件继续归档真实源码、未声明但实际存在的依赖、相对链接和命令包装；缺少可验证依赖时保留源码并报告不完整，不伪称可以运行。
- 恢复旧 v4 备份时仍读取用户插件关系，但丢弃其中的系统插件字节，并用当前 APK 的受管路径重建系统插件。
- 当 `.disabled` 与旧 bundle、旧依赖声明或旧实体同时存在时，用户的禁用选择优先。旧实体移出加载路径，原字节保留在 `.dsha-system-plugin-quarantine`，不会再次被启动扫描加载。

这项修复用于避免覆盖更新后“新 APK + 旧缓存/旧系统插件实体”混装，同时保持用户自装插件和禁用选择。插件发现回归 16 项通过、4 项因平台能力跳过；备份回归 46 项通过、15 项因平台能力跳过；插件审阅 9 项通过、1 项跳过；安装事务 5/5、依赖冻结 6/6 均通过。

### proroot JSON 存储兼容 V2

build 140 在目录项类型未知时尝试 `lstat`；部分 proroot/bind 组合连该探针也不可用，仍可能出现记录已写入、重开却读不到的情况。V2 对 `per-record` 布局使用普通字符串目录项，并只读取 descriptor 已声明的表目录；表内仍校验 `.json` 文件名、键名、记录版本和内容。这样不依赖 `DT_UNKNOWN` 的类型判断，也不需要对 bind 目录执行 `lstat`。

新运行时归档包含 `DSHA_PROROOT_DIRENT_FALLBACK_V2`，对应 storage-json 模块不再包含 `withFileTypes`。磁盘格式、会话、配置、API Key、工作区和插件数据均不迁移。

### 试运行记录不再永久耗尽

旧实现累计到 32 个 RuntimeTrial 目录后会拒绝新试运行，即使这些记录都已结束。现在只轮换已确认关闭的记录，分别保留最近 3 条成功和 5 条失败；未关闭现场、损坏的关闭标记和仍需恢复的 payload 永不自动删除。连续 33 次成功/失败交错试运行以及中断恢复后继续轮换均有单测覆盖。

### 格式化的可再生缓存竞态

WebView、`cache` 与 `code_cache` 可在格式化期间被 Android 或渲染进程重新创建，导致最终删除目录时报 `FILESYSTEM_39` / `ENOTEMPTY`。build 141 对这些明确列出的可再生目录进行有界重试；若写者持续存在，则完成核心数据格式化并显示可诊断警告。

该降级不适用于会话、插件、配置、API Key、运行时或其它核心私有根；这些位置发生相同错误仍会让格式化失败。用户取消也不会转成成功。格式化相关定向 Java 回归 13/13 通过。

### 运行维护残留与卡顿

真机取证发现，proroot 的安全试运行实际命令把 `--argv0` 写成 `/usr/local/bin/node`，旧判据只接受字面量 `node`。停止器因此把真正的 `dsha-recovery-*` Web 负载误判为其它进程、关闭记录却留下约 184 MiB RSS 的孤儿进程。build 141 最终修订：

- 按真机 NUL 分隔命令行识别 `node`/`nodejs` 的受管绝对路径，并以回归测试锁定该形态。
- 本轮 payload 按 PID、启动时刻、直接 dsh 命令和 profile 再次核验；停止结果不再静默丢弃。
- 对已有 `launched` 记录但 payload 已由旧版本清掉的安全 profile，只在两次内核身份一致且 UUID/profile 精确对应时回收，不按名称或裸 PID 批量终止。
- 维护页轮询由 500 ms 调整为 1 s，短时复用只读维护状态；安装日志和启动日志只在修订变化时重新格式化，避免反复处理 48 KiB 文本。
- WebView 文档起始脚本已安装时不再在 `onPageFinished` 重注入整份兼容脚本；同一页面的成功插件事件和后端 ready 事件保持幂等，错误事件仍完整保留。
- 空闲缓存清理改走统一数据任务屏障，自动安全停止 Web/终端，不再让用户先手工停止后仍遇到 `STOP_DSH`。

维护错误码会映射为可操作的中英文说明并保留原始码。事务创建端与读取端统一使用 64 条有界上限，避免旧 32 条门禁在没有未完成事务时永久阻止维护。

### 平板高刷新率与网页触摸热路径

M367FC/API 37 面板支持 60/90/120/144 Hz，但旧 WebPreview 窗口没有刷新率投票，静止后由系统按 60 Hz 处理。原生 MainActivity 在真机往返滑动中的现代 jank 仅约 0.25%，瓶颈集中在网页层：阅读位置监听会对每个 scroll 事件同步遍历 DOM、序列化并写 `localStorage`；触屏文件按钮与后台任务弹层的两个全页 `MutationObserver` 又会被流式消息节点持续唤醒。

最终修订包括：

- WebPreview 前台按相同分辨率的设备模式和用户 `peak_refresh_rate` 选择高刷，默认最高 120 Hz；不越过用户上限，省电模式返回系统策略，Activity 暂停后清除请求。
- API 35+ 同时向可见 View 声明 High 帧率类别，旧系统仍使用窗口刷新率提示；纯逻辑策略有独立单测，并保留 Low/API 23 编译路径。
- 阅读位置把同一帧内同一滚动容器的事件合并，存储延迟 180 ms 且仅在状态变更时写入；退出前仍强制刷新。驻留输入框扫描由 250 ms 调整为 750 ms。
- `dsh-web-mobile` 更新为 `2.4.1-dsha.6`。触屏文件按钮和任务弹层只响应各自控件所在子树的变化；菜单不存在时，捕获式 scroll 不再创建动画帧或全页查询。

在覆盖安装后的真实内置插件长列表上执行 20 次往返触摸滚动，SurfaceFlinger TimeStats 记录 WebPreview 层 733 帧、0 dropped、0 janky，120 Hz display/render，平均 114.068 FPS；该层投票为 120 Hz，触摸期间 View 类别为 High。退出工作台后 WebPreview 层被移除，MainActivity 保持 Normal 类别，没有遗留 High 请求。此结果证明本机滚动链路，不代表每种第三方插件、超长会话或其它厂商 WebView 都能恒定 120 FPS。
