# build159：数据入口归组与安装、格式化性能修订

版本 `0.2.10-20261005.1200-dsh0.2.0-rc.2` / `159`，本地交付日期 **2026-10-05**。两版继续使用包名 `com.dsh.client`、E7E3 历史发布证书和非调试正式构建；DSH `0.2.0-rc.2`、Ubuntu 基础环境 `10`、原始离线归档保持不变。

## 已完成的改动

- 「作品与文件导出」「储存指南」「技能（Skills）」集中到设置内的「数据与备份」。移除设置页的三个并列入口及顶栏快捷菜单；备份操作页也不再重复放作品和指南按钮。顶栏恢复关于按钮，安装页保留相关说明的上下文帮助链接。
- 签名资产解压保留最多 128 个本次写入 FD 的副本，先成组写回，再逐个 `fsync` 检查结果。包括旧内核在内，仍检查同一写入身份的同步错误，不能只调用一次 `syncfs` 就宣称成功。文件、目录、CRC、取消和最终根身份核验继续执行；在限制目录权限之前完成文件核验，再用已持有的目录 FD 同步权限变更。
- 格式化和整树摘要使用一次性、最多 64 个目录 FD 的会话。实际打开、列举和删除仍逐层执行 NOFOLLOW 和 inode 核验；不再对每个文件反复从 `/` 打开完整目录链。删除边界、取消、目录被替换、核心数据删除失败及缓存警告规则保持。
- 整树摘要一次共用一个 64 KiB 缓冲，避免为每个文件重新分配数组；摘要算法、完整内容读取及源文件前后核验保持一致。

## 真机短时性能对比

在同一台 Android 13 手机上，从 build158 和最终 build159 正式 APK 直接提取实际 DEX/JNI，在 shell 自有的独立 `/data/local/tmp` 目录运行同一夹具。样本为签名 DSH 归档中 **1024 个小文件 / 1,009,244 字节**，实际清理 **1237 个目录项**。这些时间只表示对应操作，未包含整个应用首次安装的离线 dpkg、运行试验、设置及 Web 启动。

| 操作 | build158 | build159 | 本次样本耗时下降 |
|---|---:|---:|---:|
| 解压小文件 | 1461.63 ms | 1249.08 ms | 14.54% |
| 完整树摘要 | 646.47 ms | 415.77 ms | 35.69% |
| 私有树目录清理 | 531.49 ms | 237.02 ms | 55.40% |

1024 个文件的 SHA-256 全部符合输入，整树摘要相同；FD 数均为 50 → 50，指向外部对照目录的链接只删除链接本体，外部文件保留。临时夹具逐个核验后清理完成，没有执行用户应用数据格式化。未以短样本比例推算完整冷安装时间，不承诺首次启动恢复到几秒。

## 本轮验证范围

两版各 **41 项受影响检查通过，0 失败、0 跳过**。覆盖解压、完整格式化边界、冷安装事务，以及两个直接相关的受管运行时摘要/回切用例。Release Lint 无 Error/Fatal；Standard 223、Low 153 条既有 Warning。最后一次受影响测试、两版 Lint 与签名构建共 **65.78 秒**。中间发现目录权限同步顺序和移除菜单后的无用资源问题，已修正；误包含的千条历史事务压力用例已中止，并改为只执行两个相关用例，没有重跑旧完整矩阵。

两版实际 APK 已检查包名、版本码、E7E3 证书、v1/v2/v3、非调试、最低 API 30/23 和 arm64。新 `libtermux.so` 以 API 23 重编，实际 LOAD 16 KiB 对齐、4 KiB/16 KiB RELRO 和新增 JNI 导出经编译脚本检查；其余 native 库和全部生成归档与 build158 逐字节一致，沿用原证据。

同一台手机完成两版正式包同签名覆盖，首次安装时间保留。Low 完成受管更新、原生就绪、三个入口及页面打开；作品页可从 DSHA 入口浏览实际目录，该设备失效的原工作目录仍如实显示不可读。本轮没有保存或改写用户作品文件。Standard 已回装，数据与备份显示三个入口，并在原生页确认就绪。未清除用户数据、重置配置、申请额外权限或发送模型对话。Android 6/7、16 KiB 真机、全新应用冷安装及用户完整格式化未在本轮执行。
