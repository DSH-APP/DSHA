- 유지보수 중 플러그인 등록 교착 수정(P0, T139, `5f204c311`): build352에서는 runtime을 넘는 덮어쓰기 업그레이드가 유지보수 화면에서 반드시 실패했습니다. `DSHA_UPDATE_RUNTIME_V1` 동안 유지보수 트랜잭션이 이미 `.runtime-descriptor.json` / `managed-assets-v2`를 새 runtimeId로 바꾸었지만 `runtime-health/<id>.json`은 `validation.verify()`가 반환된 뒤에야 기록되므로, 트랜잭션 검증 안에서 등록을 실행하면 `environmentReady()`가 반드시 false가 되어 `ENV_NOT_READY`를 던지고 롤백했습니다(PJD110 실기에서 07:17:06 / 07:19:15 / 07:26:27 세 번 연속 실패, 유지보수 화면에 계속 머묾. 롤백 후 live runtime은 build351의 runtime). 이제 유지보수 트랜잭션의 정적 검증은 runtime 패치 확인만으로 되돌리고, 등록은 트랜잭션 커밋과 건강 영수증 기록 이후로 옮겼습니다(`EnvironmentMaintenance.registerBuiltinAfterCommit`). 등록 실패는 이미 건강한 runtime을 롤백하지 않고 진단 이벤트 `MAINTENANCE_REGISTRATION=MAINTENANCE_REGISTER_DEFERRED:<이유>`(이유는 유계·줄바꿈 없음)만 기록하며, 시작 경로가 T135의 단계별 예산 / 타임아웃 시 락 정리로 계속 재시도합니다. 유지보수 완료 문구는 "dsh와 내장 플러그인 업데이트 완료"와 "dsh 업데이트 완료, 내장 플러그인 등록 미완료로 다음 시작 시 넓은 예산으로 재시도"를 구분합니다. 순수 로직 `util/MaintenanceRegistration`(`MAINTENANCE_REGISTER_OK` / `DEFERRED`)과 단위 테스트(성공·일반 실패·너무 긴 이유·중단·메시지 없는 예외)를 추가했고, 설계 문서 `docs/design/build352-maintenance-register-deadlock-20261110.md`에 실기 증거 체인, 근본 원인, mock 단위 테스트와 CI가 막지 못한 이유, 검증 체크리스트, 교훈을 기록했습니다. **build352의 runtime 간 업그레이드 경로는 깨져 있으니 업그레이드 대상으로 쓰지 마십시오**. build353의 인수 경로는 351→353 덮어쓰기입니다.
- 테스트 패키지 "피드백 및 진단" 원탭 내보내기(T138, `d6ef0e845`): 명시적 테스트 변형(`.test` / `.debug` / `.dev`)에서만 항목이 표시되고, 정식 패키지는 `BuildConfig.TEST_PACKAGE=false`로 숨겨 두며 패키지 이름이나 실행 상태로 추측하지 않습니다. 내보낸 `DSHA-feedback-…tar.gz`는 이 프로세스의 logcat(`-d --pid=<자기 pid> -v threadtime`, 자기 프로세스만), DSH / 호스트 / 복구 로그, `last-startup-failure.log`, `diagnostic-events*`, `startup-history`(최근 5개), `maintenance`(최근 3개), `runtime-health`(최근 3개), 플러그인 트랜잭션과 완료 증명, 기기·환경 정보(모델 / 브랜드 / ABI / OS 버전 / 보안 패치 / locale / 패키지 이름과 버전 / `TEST_PACKAGE` / runtimeId / 실행 방식 / uptime과 시작·유지보수·복구 상태)를 수집합니다. IMEI, 일련번호, 계정, API key는 수집하지 않으며 모든 텍스트는 `SensitiveData`로 마스킹합니다. `util/BoundedByteTail` / `util/FeedbackCapture` / `core/TestPackageFeedbackExporter`를 추가했고, `DiagnosticExportArchive`에 매개변수화된 상한을 추가했습니다. 테스트 패키지 내보내기는 최대 48개 항목, 항목당 ≤256 KiB, 총 ≤8 MiB이며, 정식 패키지 진단 내보내기는 기존대로 32개 / 256 KiB / 1 MiB입니다. 원본이 없거나 루트를 벗어나거나 심볼릭 링크이거나 읽기 실패인 경우 manifest의 `capture` 구간에만 기록하고 전체 압축을 막지 않습니다. 저장은 "다른 이름으로 저장…"(SAF, 쓴 뒤 바이트를 다시 읽어 검증) 또는 "공유…"(시스템 공유 대상에만 전달, 네트워크 없음, 자동 업로드 없음)을 사용합니다.
