# DSHA 0.2.1-rc.5-20261106.0230-dsh0.2.2-rc.1 / build330

- Refuse de lancer l'hôte lui-même sur l'écran virtuel (T76) : `/app/vscreen/launch` n'accepte plus le paquet de DSHA lui-même comme cible. Le système ne crée pas d'instance séparée pour l'écran secondaire ; il réutilise le même processus en cours, et la WebView déjà liée à l'affichage principal plante avec un pointeur nul dans `libmonochrome` sur l'écran secondaire (preuve de l'appareil relay : display 4, Looper du thread principal entrant dans la WebView, processus 14715 en cours réutilisé). Le bridge refuse avant toute demande d'autorisation, le Manager avant le claim et le Core avant d'envoyer `am start`, tous via la même vérification, en renvoyant `VSCREEN_SELF_LAUNCH_REFUSED` (`state=NOT_SENT`, aucune commande de lancement n'est envoyée et il n'y a pas de plantage) ; le plugin intégré classe ce code en pre-dispatch, le sélecteur natif d'applications ne liste plus l'hôte et la page de résultat affiche la raison en chinois/anglais. Il s'agit d'un refus de sécurité, pas d'une prise en charge du self-launch sur écran secondaire ; pour le prendre en charge plus tard, il faudra `createDisplayContext` avec une instance WebView séparée. Le runtime descriptor est régénéré (runtimeId `35e3f499`) ; les entrées fixes ne sont pas reconstruites.
- Correctif de l'actif gh géré dans l'APK (T79, conclusion B de T78) : les APK officiels build328/329 ne contiennent que `assets/gh-cli.tar` (38 727 680 B, STORED), sans `gh-cli.tar.gz` — la fusion d'actifs d'AGP 9.1.1 gunzip automatiquement les fichiers `.gz` et supprime l'extension, donc l'installation gérée qui ouvre `gh-cli.tar.gz` échoue forcément (l'amorçage du wrapper peut encore rattraper). Le nom de l'entrée fixe source et le pin de `runtime-descriptor.json` restent inchangés et les entrées fixes ne sont pas reconstruites ; le nom d'emballage dans l'APK devient `gh-cli.bin`, `RuntimeTools` ouvre le nom emballé et retombe sur le nom source, et la nouvelle barrière de publication `tools/verify-apk-managed-assets.py` vérifie les noms de membres réels, les empreintes octet par octet et le membre gh épinglé dans les chaînes de build de production et de paquet de test, afin qu'un renommage silencieux ne puisse pas se reproduire. Le runtimeId suit la modification du générateur géré et devient `35e3f499` (les entrées fixes ne sont pas reconstruites).
