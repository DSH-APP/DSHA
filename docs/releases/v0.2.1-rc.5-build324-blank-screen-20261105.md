# build324 覆盖安装后白屏与侧边栏重复：受管运行时补丁链侧排查（2026-11-05）

> 状态：**真机对照已确认（2026-11-05）**——用户把「main + `cf174f13` 齿轮修复」的测试包装上后
> **白屏消失、且能正常触发环境重建**；即白屏/侧栏重复的触发点就是第 5 节那条「移动壳 footer
> 依赖宿主连接指示灯」的契约。直接 JS 栈仍未取到（取法保留在第 7.0 节，供以后同类问题复用）。
> 本文只覆盖 T61 范围（受管运行时补丁链 / 客户端包）。维护页门禁判定由 T60 负责。

## 1. 现象

build323（`e4f69423`）覆盖安装 build324（`eb9ec55d`）后：维护页出现但未自动开始环境更新，
「进入主界面」按钮位于维护提示之上；进入主界面后整页白屏，侧边栏有重复叠加观感。
用户在原生插件列表里**禁用内置插件 `dsh-web-mobile` 后两个现象都消失**。

## 2. 结论摘要

1. **两条新受管补丁在 324 的运行树里都干净应用了**：各自锚点唯一命中、打完后逐字节反向应用
   能还原到声明里的 `sourceSha256`，`node --check` 通过，`let hasConnectedOnceInPage` 与
   `SettingsRoot` 同处模块工厂作用域（不是 TDZ 或跨作用域引用）。**不存在「补丁应用失败被静默忽略」。**
2. **324 与 323 的运行树差异只有 4 个文件 = 2 个模块 × 2 份拷贝**（`@deepseek-ai/dsh-client-ui-settings-general`、
   `@deepseek-ai/dsh-tool-skill`），没有新增/删除/其它字节变化。因此白屏不能归因于「某处树被换坏」，
   只能来自这 2 个模块的行为差异，或来自**页面加载时机**（T60 门禁）。
3. **两条补丁里唯一的客户端可见差异落在手机侧栏 footer**：手机是 drawer 模式（`viewport < 768`），
   `wide` 因此为真，`ConnectionIndicator` 本来是真机上真实渲染的；T58 让首次连接不再渲染它，
   `dsh-web-mobile` 3.2.2 上游恰好用「这一行里有没有指示灯」决定是否往同一行注入自己的设置齿轮、
   以及是否收起账户菜单里的设置项。**这是 323 与 324 在手机上唯一能被看见的差别，也正是「侧边栏重复」所在的
   footer 行。**
4. 白屏的直接触发栈仍未取到（静态侧无法复现「一个不渲染的指示灯把整页打白」）；但**真机对照已确认
   因果**：同一份 main 内容 + `cf174f13`（只改这条契约）后白屏消失且维护流程恢复。未取到的 JS 栈
   不再阻塞修复，取法保留在第 7.0 节。**不建议在拿到该异常前改 Java 判定逻辑或重建固定输入。**

## 5. 手机上唯一客户端可见差异（T58 ←→ dsh-web-mobile 契约）

- `dsh-client-ui-layout/lib/client.js`：`const drawer = viewport < 768 && !windowsTitlebar;`（手机 = drawer）。
- `dsh-client-ui-sidebar/lib/client.js`：`const wide = drawer || (windowsTitlebar ? !collapsed : !collapsed || !settled);`
  → **手机 drawer 模式下 `wide === true`**。
- 打过 T58 的 `dsh-client-ui-settings-general/lib/client.js`：
  `state: wide && desktopUpdate.presentation?.phase !== "installing" ? connectionIndicator : void 0`。
  手机 `wide` 为真 ⇒ 指示灯状态完全由补丁后的 `connectionIndicator` 决定：
  323 首连是 `"connecting"`→`"recovered"`；**324 首连是 `void 0`（完全不渲染）**。
- [`dsh-web-mobile` 产物](../../app/src/main/assets/builtin-plugins/dsh-web-mobile/lib/client.js)：
  - 第 393 行 CSS `drawer-quick-settings-chip-guard`：`:has(> button[data-phase], > [role="status"])`
    命中时隐藏插件注入的设置齿轮；
  - 第 9127 行 `gearAvailable` 与第 9144 行 `syncMenuEntry` 用同一判据（镜像 CSS，注释明确要求两处口径一致），
    行内没有指示灯时**齿轮会被插入并保留**，同时账户菜单的「设置」项被收起。

也就是说：324 是这条 footer 行**第一次**走「没有指示灯」的分支——插件自己的齿轮首次出现在该行、
宿主账户菜单的设置项被收起。这一行正是用户描述「重复叠加」的位置。

> 该 guard 属于上游 `dsh-web-mobile` 3.2.2 源码（`tools/mobile-plugin-upstream/lib/client.js` 两处），
> 不是 DSHA 的本地补丁，`tools/apply-mobile-client-patches.mjs` 里没有它。

## 6. 已排除 / 未排除

**已排除（静态可证）**

- 补丁链应用失败被忽略：`ManagedPatchChain.apply` 在锚点不符时先尝试用包内 canonical 模块重建，
  仍不符就抛 `PATCH_CHAIN_MISMATCH`（IOException）；`patchClientCombos` / `patchBrowserBootstrap`
  的 `IllegalArgumentException` 也升格为 IOException。唯一「记录后继续」的分支是
  `PATCH_RUNTIME_VERSION_MISMATCH`（运行树 dsh 版本与 registry 不符），它只记录诊断、不应用补丁，
  不是应用失败后的兜底。
- 重复应用：marker 命中即跳过；`ExactTextPatch` 的「after 已存在且 before 计数一致」也视为已应用。
- 拼接/组合冲突：全量 client 组合脚本 `node --check` 通过。
- HTML 引导注入重复：`HtmlBootstrapPatch` 用自有 `DSHA_BROWSER_COMPAT_BEGIN/END` 区块替换，幂等。
- 前端静态缓存串版：`frontend-static-cache-patch.json` 已对渲染后的 index 明确 `no-store`，
  且模块/组合 URL 带内容 `rev`；该补丁在 323、324 两份树里字节相同。

**未排除（需要设备证据）**

- H1：页面在受管运行时事务**提交前/提交中**被加载（T60 的维护门禁没自动开始更新，用户提前进入），
  客户端拿到的是混合图或半写状态；随后禁用插件触发 Web 重启，页面在完整树上重载所以「恢复正常」。
- H2：T58 让 footer 行首次走「无指示灯」分支后，上游插件注入的非 React 节点与 React 子节点核对冲突
  （插件自己在 `stats-line` 注释里记录过同类 `NotFoundError` 会让 `SlotErrorBoundary` 清空槽位），
  表现为内容区白屏 + 侧栏多出一条设置入口。
- H3：WebView 里两层页面叠加（旧页 + 新页），需要设备侧确认 DOM 里是否只有一个 `#root`。

## 7. 设备侧取证清单（供主会话转给用户）

### 7.0 白屏栈：3 步取（最小操作）

主 WebView 没有原生 console 捕获（只有内嵌预览有），所以这条栈**只能从 WebView 的 console 走**：

1. 手机「设置 → 关于手机」连点版本号开「开发者选项」→ 打开 **USB 调试**，用数据线连电脑。
2. 电脑执行 `adb logcat -c`，然后 `adb logcat -s chromium:V *:S | grep -E "CONSOLE|DSHA_PAGE"`。
3. 手机上重新进入主界面复现白屏，把 `chromium … CONSOLE(...)` 或 `[DSHA_PAGE] {"type":"issue"…}`
   的第一段（含 `Uncaught` / `Failed to load` / `NotFoundError` 字样）整段复制出来交给主会话。

**取不到时**（用户没有电脑/不能开 USB 调试）：改用 App 内 **设置 → 诊断 → 导出故障包**
（含脱敏启动记录与操作记录尾部，可直接分享文本），再补一条 guest 侧 `/root/.dsh/logs/`
最近一次启动日志；这两份足以判定第 6 节的 H1（事务未提交就加载页面）是否成立。

按顺序取，全部在**已装回 build324 后**做；不要先禁用插件（否则错过第一次现场）：

1. **WebView console（最关键）**：在 App 内打开主界面 → 复现白屏 → 用 `chrome://inspect`（USB 调试）
   或 App 内置的「导出日志」抓 `console` 的 `error`/`unhandledrejection` 第一条栈；
   `web-integration/startup.js` 会把插件加载失败写成 `[DSHA_PAGE] {"type":"issue",…}`，
   这条日志会同时出现在 `logcat` 与页面事件里。
2. **logcat 关键字**：`adb logcat -d | grep -Ei 'DSHA_PAGE|chromium|PATCH_|runtime|dsh'`；
   重点看有没有 `PATCH_CHAIN_MISMATCH`、`PATCH_RUNTIME_VERSION_MISMATCH`、`Missing static module`、
   `NotFoundError`、`SlotErrorBoundary`。
3. **guest 侧运行树自证**：导出（只读）`/root/.dsh/logs/` 下最近一次启动日志、`/root/.dsh/` 下的
   维护/事务回执；确认 `usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-client-ui-settings-general/lib/client.js`
   的 sha256 是否为 `1966babc2bfa507a3953e65f15255bb612b4b63b7440c6a8c4c63606fa968141`
   （若是别的值 = 树没更新到 324 或混合树）。
4. **侧栏 DOM 快照**：白屏时在 WebView 里执行一次
   `document.querySelectorAll('#root').length` 与
   `document.querySelectorAll('[data-mobile-nav="frame"]').length`，
   再 `document.querySelectorAll('[class*="triggerRow"]').length`；三者都应为 1。
   任何一项 >1 就证实 H3（两层页面/两份帧）。
5. **时间线**：记录「点进入主界面」与维护事务完成的时间先后（维护页阶段列表 + 启动日志时间戳）。
   若页面先加载、事务后提交，H1 成立。
