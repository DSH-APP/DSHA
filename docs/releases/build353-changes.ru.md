# DSHA 0.2.1-rc.5-20261110.0900-dsh0.2.2-rc.1 / build353

- Исправление взаимной блокировки регистрации плагинов при обслуживании (P0, T139, `5f204c311`): в build352 обновление перезаписью между runtime всегда срывалось на странице обслуживания — во время `DSHA_UPDATE_RUNTIME_V1` транзакция обслуживания уже переключала `.runtime-descriptor.json` / `managed-assets-v2` на новый runtimeId, а `runtime-health/<id>.json` записывается только после возврата `validation.verify()`; поэтому регистрация, выполняемая внутри проверки транзакции, видела `environmentReady()` гарантированно ложным, выбрасывала `ENV_NOT_READY` и откатывалась (OnePlus PJD110, три подряд отказа в 07:17:06 / 07:19:15 / 07:26:27, приложение оставалось на странице обслуживания; после отката активный runtime был из build351). Теперь статическая проверка транзакции обслуживания снова ограничена проверкой патча runtime, а регистрация перенесена после фиксации транзакции и записи свидетельства здоровья (`EnvironmentMaintenance.registerBuiltinAfterCommit`); сбой регистрации больше не откатывает уже здоровый runtime, а только записывает диагностическое событие `MAINTENANCE_REGISTRATION=MAINTENANCE_REGISTER_DEFERRED:<причина>` (причина ограничена, без переводов строк), и путь запуска продолжает повторять попытки с многоуровневым бюджетом / очисткой блокировки по таймауту из T135. Текст завершения обслуживания различает «dsh и встроенные плагины обновлены» и «dsh обновлён; регистрация встроенных плагинов не завершена и будет повторена с широким бюджетом при следующем запуске». Добавлена чистая логика `util/MaintenanceRegistration` (`MAINTENANCE_REGISTER_OK` / `DEFERRED`) с модульными тестами (успех, обычный сбой, слишком длинная причина, прерывание, исключение без сообщения); проектный документ `docs/design/build352-maintenance-register-deadlock-20261110.md` фиксирует цепочку доказательств с устройства, корневую причину, почему mock-тесты и CI это не поймали, контрольный список проверки и выводы. **Путь обновления между runtime в build352 сломан; не используйте его как цель обновления** — путь приёмки build353 — перезапись 351→353.
