# DSHA 0.2.1-rc.5-20261109.2300-dsh0.2.2-rc.1 / build350

- Preuve de fenêtre minimale et indice actionnable en multi-fenêtres pour l'écran virtuel (T98, `33ceab2c7`) : les réponses `FRAME_NOT_READY` détaillées de `see` et les réponses « fenêtre indisponible » de tree / node / editor / anchor portent désormais un instantané de fenêtre minimal en lecture seule lorsque l'accessibilité peut lire les fenêtres (`util/VirtualScreenWindowEvidence`) : nombre de fenêtres d'application / système / méthode de saisie, `focusedWindowId` / `activeWindowId`, `windowAmbiguous`, et — uniquement lorsqu'une seule fenêtre est sélectionnable — displayId / id / type / layer / bounds / focused / active / titre / paquet de la fenêtre cible. Les titres perdent les caractères de contrôle, les espaces sont repliés et le texte est tronqué à 64 points de code ; les paquets ne sont conservés qu'après validation du format de nom de paquet, et toute autre valeur invalide est omise. L'instantané ne contient ni texte de nœud, ni contenu de contrôle, ni capture d'écran, ni liste complète des fenêtres. `NO_UNIQUE_APPLICATION_WINDOW` distingue désormais deux causes par les compteurs : plusieurs fenêtres d'application côte à côte (écran partagé / fenêtre flottante) → `reason=VSCREEN_WINDOW_AMBIGUOUS`, `nextAction=ASK_USER_TO_CLOSE_SPLIT_SCREEN` ; uniquement des fenêtres système / de méthode de saisie et aucune fenêtre d'application → `reason=VSCREEN_NO_WINDOW`, `nextAction=LAUNCH_APP_FIRST`. La preuve ne sert qu'à expliquer l'échec et l'étape suivante et **ne participe jamais à l'autorisation, au choix de fenêtre ou aux nouvelles tentatives** : le chemin sémantique n'accepte toujours que le résultat unique de `VirtualScreenWindowPolicy.selectDetailed`, et le chemin d'ancrage n'accepte que le windowId de l'observation d'origine (un id répété reste rejeté comme `ANCHOR_WINDOW_AMBIGUOUS`) ; une situation « multi-fenêtres » ne bascule jamais silencieusement vers une autre fenêtre.
- Paliers d'écran sensible et remise à l'utilisateur sur l'écran virtuel (T119, `dc6f9642e` / `c3a4e3c30` / `241e06159`) : nouveaux `util/SensitiveScreenClassifier` et `util/SensitiveScreenPolicy` (logique pure) qui ajoutent une classification prudente de l'écran entier par-dessus le garde-fou strict du focus mot de passe du 6.1 (mot de passe / code à usage unique / paiement / sécurité système / sensible mais illisible `SECURE_UNKNOWN`), avec `ASK` par défaut pour chaque catégorie ; chaque catégorie peut être réglée sur `HANDOFF` — suspendre l'assistant avant d'envoyer la moindre saisie, révoquer les requêtes en cours et jeter les observations, en renvoyant `ok:false` / `state=NOT_SENT` / `error=SENSITIVE_SCREEN_HANDOFF` / `sensitivity=<catégorie>` / `readOnly:true` / `retryable:false` / `nextAction=HANDOFF_TO_USER` ; après reprise par l'utilisateur, l'assistant doit refaire `see` et ne rejoue jamais automatiquement. `OFF` ne désactive que les paliers d'écran entier et revient à la politique de confirmation ordinaire. La lecture/écriture du texte de mot de passe reste bloquée durement dans la couche de saisie et n'est levée par aucun palier ni confirmation. `ALLOW_ALL` et `ALLOW` par application ne sautent que les confirmations ordinaires et ne peuvent pas contourner un `ASK` sensible ; une confirmation sensible est à usage unique et **n'est pas écrite dans la mémoire de 5 usages « autoriser cette application pour ce tour »** (les applications ordinaires redemandent toujours tous les 5 usages). Réglages → Autorisations des capacités de l'appareil → Observation d'écran gagne une ligne distincte « Remise d'écran sensible » avec demande / remise par catégorie et deux listes de noms de paquets exacts (remise forcée et applications de confiance ; vides par défaut, 64 au maximum chacune, mutuellement exclusives, données corrompues revenant à ASK). Le `policyRevision` de l'écran combine les révisions `screen_confirmation_v1` et `sensitive_screen_v1`, donc tout enregistrement invalide les anciennes confirmations et les requêtes en cours, avec une borne inférieure monotone dans le processus ; les points d'entrée qui injectent de la saisie reclassifient après confirmation et avant envoi — un écran illisible renvoie `SENSITIVE_SCREEN_UNVERIFIED`, une catégorie changée renvoie `SENSITIVE_SCREEN_CHANGED`, les deux non envoyés et à réobserver.
- Corrections de l'îlot (capsule de notification) (PR #12, `ccd4b81d7`, déjà dans main) : la vue déployée ne garde qu'un seul indicateur de tour (subText de la notification), le corps ne répète plus « Tour N » et aucune valeur de secondes n'est écrite chaque seconde pendant l'exécution, donc la signature de contenu reste stable et les reconstructions par battement ne gobent plus les appuis sur les boutons d'option ; les échecs de réponse en arrière-plan doivent être visibles — HTTP non 200, envoi vide, options expirées ou entrée morte affichent un Toast (avec le statut HTTP et le code d'erreur du serveur, par exemple `HTTP 409 NO_WAITING`) et invitent à ouvrir la conversation, tandis que le journal de l'application enregistre `TASK_ANSWER_REJECTED <status> <body>` ; ouvrir la conversation depuis la notification vérifie désormais la présence d'une vraie ligne d'options (`Mbwy4a_optionRow`) — le conteneur `Mbwy4a_options` est rendu pour chaque carte et serait toujours vrai — et, en présence d'options, ne vole pas le focus et laisse le clavier fermé pour que le bouton « Envoyer » en bas de carte ne soit pas poussé hors de l'écran. `docs/island-status.md` porte désormais un tableau d'état de vérification par plateforme : Android natif 16, 16 QPR1+, HyperOS, ColorOS 16 et OriginOS 6/7 sont marqués ligne par ligne (prise en charge par branche de plateforme / prise en charge dans le code sans test sur appareil / observation de contributeur sur appareil non commitée / informations publiques sans test sur appareil / prise en charge attendue sans trace sur appareil), et OriginOS 7 (Android 17) est explicitement indiqué sans aucune trace d'exécution sur appareil dans le dépôt.
