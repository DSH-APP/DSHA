- 上書きアップグレード後の初回起動におけるプラグイン登録の修正（T135、`092b8848d`）：登録予算を管理対象アセットの身元で段階化しました（通常 90 秒、初回 240 秒）。ホストは `runtime-descriptor` の `runtimeId` を、guest は `managed-assets-v2` を読み、登録成功後に `register-managed-asset-id` を原子的に書き込みます。タイムアウトで強制終了された場合は書き込まれないため、次回も広い予算で再試行します。登録スクリプトは `--clear-stale-profile-lock` を追加（`operation_lock` を経由せず、終了が確認できた保持者のロックだけを削除）。ホストは登録タイムアウト後に 10 秒の短い予算で一度だけ掃除します。`plugin-manager list` は死んだ保持者に対して `PLUGIN_PROFILE_LOCK_STALE`（再試行可能）を返し、「設定を変更中」という曖昧な報告をやめました。`StartupRecoveryState` に `Kind.REGISTER` を追加し、`BUILTIN_REGISTER_TIMEOUT` / `EXIT_` / `RECEIPT_MISSING` と `PLUGIN_PROFILE_LOCK_TIMEOUT` / `STALE` を識別します。タイトルと説明は「プラグイン登録のタイムアウト / 未完了 / 確認待ちのロック、そのまま再試行できます」を示し、`StartupText` は行動可能な結論だけを残して生の `exit=` / `timedOut=` / guest JSON を外します（原文は起動履歴とログに残ります）。ホスト側の段階計時：登録コマンドは Runner の行コールバックを通り、失敗メッセージに `hostElapsedMs` と最後の `REGISTER_TIMING` 段階を追加し、guest の自己申告時間がホストの実時間を超える場合は `GUEST_TIMING_MISMATCH` を明示します。初回起動でオーバーレイを二重にインストールしない：`RuntimeTools` がプロセス間の `.runtime-tools-prepared` 完了スタンプ（相対的な管理対象ファイル集合 + `RuntimeAssetStamp`）を書き、APK 身元・登録済み descriptor 身元・メタデータスタンプがすべて一致する場合のみ再利用し、不一致なら完全な準備に戻します。登録をメンテナンスの準備完了チェックに統合：update の `RuntimeTrial` 静的検証を `register=true`、`requireCompleted` + `BUILTIN_REGISTER_OK` に変更し、Web 試運転の前に登録を完了、失敗はトランザクションとともにロールバックします。`RegisterBudget` / `GuestTimingEvidence` / `RuntimePreparedProof` の単体テストと、登録予算・計時証拠・タイムアウト時のロック掃除・`REGISTER` 分類・`StartupText` 折り畳みのケースを追加し、`tools/` にロック状態 / 引継ぎ / 掃除、身元マーカー、stale ロック一覧のテストを追加しました。**479409ms を単一のサブ段階に帰属させず**、ホストと guest の両側の時間と最後の段階だけを診断に記録します。上書きアップグレード後の初回起動はまだ実機検証が必要です。
