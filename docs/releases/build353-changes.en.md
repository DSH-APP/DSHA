# DSHA 0.2.1-rc.5-20261110.0900-dsh0.2.2-rc.1 / build353

- Maintenance-time plugin registration deadlock fix (P0, T139, `5f204c311`): on build352 an overwrite upgrade across runtimes always fails on the maintenance page — during `DSHA_UPDATE_RUNTIME_V1` the maintenance transaction has already switched `.runtime-descriptor.json` / `managed-assets-v2` to the new runtimeId, while `runtime-health/<id>.json` is written only after `validation.verify()` returns, so registration running inside the transaction validation sees `environmentReady()` as false, throws `ENV_NOT_READY` and rolls back (OnePlus PJD110, three consecutive failures at 07:17:06 / 07:19:15 / 07:26:27, stuck on the maintenance page; after rollback the live runtime was still build351's runtime). The maintenance transaction's static validation is restored to runtime-patch checks only, and registration now runs after the transaction commits and the health receipt is written (`EnvironmentMaintenance.registerBuiltinAfterCommit`); a registration failure no longer rolls back the already-healthy runtime but only records the diagnostic event `MAINTENANCE_REGISTRATION=MAINTENANCE_REGISTER_DEFERRED:<reason>` (bounded, single-line reason), while the startup path keeps retrying with T135's tiered budget / timeout lock cleanup. The maintenance completion text now distinguishes "dsh and bundled plugins updated" from "dsh updated; bundled plugin registration is not finished and will be retried with the wide budget on the next start". New pure logic `util/MaintenanceRegistration` (`MAINTENANCE_REGISTER_OK` / `DEFERRED`) with unit tests covering success, ordinary failure, over-long reason, interruption and message-less exceptions; the design note `docs/design/build352-maintenance-register-deadlock-20261110.md` records the device evidence chain, root cause, why mock unit tests and CI did not catch it, the validation checklist and lessons. **build352's cross-runtime upgrade path is broken; do not use it as an upgrade target** — build353's acceptance path is a 351→353 overwrite.
- Test-package "feedback and diagnostics" one-tap export (T138, `d6ef0e845`): the entry is shown only in explicit test variants (`.test` / `.debug` / `.dev`); the formal package keeps `BuildConfig.TEST_PACKAGE=false` and stays hidden, never guessing from the package name or runtime state. The exported `DSHA-feedback-…tar.gz` collects this process's logcat (`-d --pid=<own pid> -v threadtime`, own process only), DSH / host / repair logs, `last-startup-failure.log`, `diagnostic-events*`, `startup-history` (last 5), `maintenance` (last 3), `runtime-health` (last 3), plugin transactions and completion proofs, plus device and environment information (model / brand / ABI / OS version / security patch / locale / package and version / `TEST_PACKAGE` / runtimeId / runtime mode / uptime and startup, maintenance and recovery state); IMEI, serial number, accounts and API keys are not collected, and all text goes through `SensitiveData` redaction. New `util/BoundedByteTail` / `util/FeedbackCapture` / `core/TestPackageFeedbackExporter`; `DiagnosticExportArchive` gains parameterised limits — the test-package export is at most 48 items, ≤256 KiB per item and ≤8 MiB total, while the formal diagnostic export stays at 32 items / 256 KiB / 1 MiB; missing sources, out-of-root paths, symlinks or read failures only enter the manifest `capture` section and never block the archive. Saving uses "Save as…" (SAF with byte read-back verification) or "Share…" (system share targets only, no network, no automatic upload).
- Formal Release carrying coexisting test packages and dry_run (T137, `393fdd362`): a new shared node `_node-test-packages.yml` builds `.debug` (debuggable) and `.dev` (release, non-debuggable) coexisting test packages by matrix, signs them with an independent test certificate, verifies package-name suffix, version, debuggable, and that the certificate differs from both the formal and upstream certificates, and re-runs verify-dsh-upgrade / recovery / third-party / managed-assets. `release-production.yml` gains `test_packages` (`debug+dev` default / `debug` / `none`) and `dry_run` inputs; `test-packages` runs in parallel with `build-signed`, and `publish` downloads the test-package evidence and merges the `testPackages` section, `SHA256SUMS` and release notes through `tools/release-test-packages.py`, which ships with the evidence and is checked against the build-info digest; with `dry_run=true` publish is skipped and `dry-run-summary` performs the same merge / verification and prints the tag and asset digests it would create. Test-certificate secrets go only to that node, live only in `RUNNER_TEMP` and are deleted under `if: always()`; `test-package-variants.yml` reuses the same node, and the formal Release requires the fixed test certificate (one-off certificates are rejected). New `tools/release-test-packages.py` with 16 unit tests (same run / same commit, APK digest, certificate PEM, `SHA256SUMS` self-consistency, path traversal and double-merge counterexamples).
