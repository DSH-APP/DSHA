## 一、本版针对

用户报告：build323 覆盖安装 build324 后，维护页把「进入（受限）主界面」摆在上位、
更新没有自动开始；进入后主界面白屏。两条独立的缺口，本版修其中与**维护门禁展示/入口**
有关的那一条：

| 现象 | 归属 |
|---|---|
| 维护页把「进入主界面」升为主操作，更新降为次要按钮 | **本版（T60）** |
| 同 dsh 版本、只换受管补丁的覆盖安装被判成「无事可做」 | **本版（T60）** |
| 受限入口不记「补丁级未完成」，进主界面即被门禁弹回 | **本版（T60）** |
| 未确认旧 Web 会话把维护页挡掉，唯一修复入口消失 | **本版（T60，第二笔）** |
| 侧栏重复叠加 / 白屏的直接触发点 | T61 / build325（`DSHA_GEAR_FIT_V1`） |

判定层（`EnvironmentAccess.requiresMaintenanceBeforeStart`、`EnvironmentIdentity.shouldBlockRuntimeStart`）
在两条路径上都判对了，本版**没有改**这两个函数，也没有改
`WebLifecycleController` 的启动准入（契约 I5）。

## 二、根因（一句话版）

`RuntimeInstallationState.isEnvironmentReady()` 只回答「旧树还能不能用」（兼容性 + 健康回执），
不回答「是不是当前候选」（`RuntimeDescriptor.latest` 比较 `runtimeId` 与 `inputs`）。
323→324 是同一 dsh 版本、只换受管补丁，所以 `compatible()` 恒为真：维护页据此认为
「无事可做」，把「进入主界面」升为主操作；受限入口也不记限制身份，主界面门禁随即把用户
送回维护页；`EnvironmentUiStatus` 同样只看 `isEnvironmentReady()`，受限主界面里没有回到
维护页的入口。旧 proot Web 仍存活时 `hasUnresolvedWebSession()` 为真，
`shouldAutoStart` 拒绝自动开始（**正确且必须保留**的安全门禁），于是维护永远不会开始。

## 三、本版改动（两笔提交，逐步可回滚）

1. **补丁级判定与维护页展示**
   - 新增纯逻辑 [`util/RuntimeUpgradeState.java`](../../app/src/main/java/com/deepseekharness/app/util/RuntimeUpgradeState.java)：
     `upToDate` / `maintenanceRequired` / `limitedEntry` / `openMaintenancePage`；
   - [`ExtractActivity`](../../app/src/main/java/com/deepseekharness/app/ui/ExtractActivity.java)：
     维护页「就绪」= 环境可继续运行 **且** 已装运行时就是当前候选；`proceed()` 的受限入口
     计入补丁级未完成；已安装但陈旧时给出「内置补丁尚未落地」的警示说明（仅已安装场景，
     首次部署不显示）；
   - [`EnvironmentUiStatus`](../../app/src/main/java/com/deepseekharness/app/ui/EnvironmentUiStatus.java)：
     主界面环境横幅的受限提示同样覆盖补丁级未完成，受限主界面里保留回维护页的入口；
   - 新增回归 [`OverwriteUpgradeGateTest`](../../app/src/test/java/com/deepseekharness/app/backup/OverwriteUpgradeGateTest.java)
     与 [`RuntimeUpgradeStateTest`](../../app/src/test/java/com/deepseekharness/app/util/RuntimeUpgradeStateTest.java)。
2. **入口放开（只放页面，不放自动开始）**
   - [`MainActivity.checkEntry`](../../app/src/main/java/com/deepseekharness/app/ui/MainActivity.java)
     改用 `RuntimeUpgradeState.openMaintenancePage(failed, maintenance, restoring)`：
     `unresolved` 不再是打开维护页的前置条件；
   - `EnvironmentIdentity.shouldAutoStart(..., unresolvedWebSession)` 原样保留：存在未确认
     原实例时自动开始仍返回 false，用户必须在维护页手点一次。

`OverwriteUpgradeGateTest` 里「包内描述符」那条回归**不绑定 build 号**：它从当前
`runtime-descriptor.json` 克隆一份「同 dsh 版本、只换受管输入」的前代再断言，所以 build326
及以后每次重算 `runtimeId` 都仍然成立。

## 五、本版不改的东西

- 不改 `requiresMaintenanceBeforeStart` / `shouldBlockRuntimeStart`（判定层本来就是对的）。
- 不改 `WebLifecycleController` 的启动准入，不为「消灭白屏」放宽门禁。
- 不改任何受管运行时输入（`dsh-runtime.bin` 摘要仍
  `c1bd68330a10776f304a92a19d8f82c184c1abf523275a9e28dbb2c2e764e4fe`），
  不需要重建 fixed-inputs，也不需要同步 `ci/sunset-inputs.lock.json`、
  `docs/fixed-build-inputs*.md`、`tools/recovery-runtime/lock.json`。
- 不改内置插件与受管补丁，第三方声明不需要重算（仍按当前锁通过）。

## 六、真机验收清单（用户核对用，未验证前不算通过）

> 同一份 APK 的两个场景都要看：**S1 是主场景**（设备现在停在 build299），
> **S2 是补丁级路径的对照场景**（需要一台仍停在 build323/324 且环境是旧受管树的设备）。

### 场景

- **S1（主场景）**：build299 → build326 覆盖安装（同包名、同签名、非调试）。
  299 的受管树不是当前候选，走的是「受管树整体更新」路径，同样必须落在整屏维护页。
- **S2（对照场景）**：build323 或 build324 → build326 覆盖安装。这是**补丁级**路径
  （同一 dsh 版本、只换受管补丁与描述符输入），是本版修复的核心场景。
- 每个场景再分两种时机：「旧 Web 仍在运行」与「先正常停止 DSH 再覆盖」。

### A. 主判据（A1–A5）

- **A1** 安装后首次启动停在整屏「运行环境维护」页，不是主界面，也不是空白 Web。
- **A2** 竖屏：**最上方**的大按钮是实心主色 **「更新运行时」**（若上次维护记录未完成则是
  「恢复中断维护」）；它**下面**才是描边次要按钮 **「进入受限主界面 · 查看日志与配置」**。
  横屏（≥600dp）时为并排：主操作在右、受限入口在左。
  → 修复前是反的（上面是「进入主界面」），这是本条修复最直接的观察点。
- **A3** 说明区为黄色警示，含
  「已安装的运行环境仍是上一版的受管运行时，本次内置补丁尚未落地。请先完成这次维护；也可以进入受限主界面查看日志与配置。」
  （S1 从 299 覆盖时，若受管树差得较多，可能显示维护失败/待恢复类文案，此时以「更新运行时
  是主操作、且可点」为准。）
- **A4** 覆盖前旧 Web 仍存活时，**不会自动开始**（契约 I4：不自动重放未确认实例），
  这是合格行为；点「更新运行时」→ 安全确认对话框 → 顶部变「维护中」进度面板（阶段卡）→
  结束后主操作变为 **「进入主界面」**，A3 的警示消失。
- **A5** 完成后点「进入主界面」：没有「受限模式：环境需要恢复」横幅；Web 正常加载；
  可见 T54 技能调用一次性确认弹窗、T58 首次进入不闪黄/绿（证明两条受管补丁已落地）。

### B. 强制回归（B1–B3）

- **B1** UI-only 覆盖（同一 build 重装，或描述符未变的包）→ 直接进主界面，不出现维护页，
  桌面图标启动正常（契约 I6）。
- **B2** 在维护页点「进入受限主界面」→ 主界面顶部出现
  「受限模式：环境需要恢复 / 终端、Web 与插件暂不可用 · 点按处理」横幅；点横幅回到维护页；
  再从桌面图标进入仍停主界面（同一 APK 身份只记一次，不来回跳，契约 I7）。
- **B3** `INSTALLED_NEWER`（个人数据由更高 dsh 代次写入）仍只提示、不自动修复，
  维护页给出「导出可读副本」入口。

### C. 取证（C1–C4，可选，不改任何状态）

- **C1（免 root，最容易做）** 维护记录页（维护页底栏「维护记录」，或主界面 → 诊断）里
  「运行时版本与身份」：更新前显示 **「存在版本差异」** + 旧 `runtimeId`；更新完成后变成
  **「与包内版本一致」**。
- **C2（入口门禁日志）** 抓 `MAIN_ENTRY_GATE`：覆盖后首次启动应为 `maintenance=true`
  （即使 `unresolved=true`，这正是第二笔提交的行为）；从维护页选了「进入受限主界面」后
  再次启动应为 `maintenance=false`。
- **C3（受管补丁标记，需要 root）** 更新完成后两个标记各 ≥1，更新前应为 0 / 文件不存在：
  - `DSHA_USER_ONLY_SKILL_APPROVAL_V1`
    在 `files/linux/ubuntu/usr/local/lib/node_modules/@deepseek-ai/dsh-tool-skill/lib/index.js`
  - `DSHA_FIRST_CONNECT_SILENT_V1`
    在 `files/linux/ubuntu/usr/local/lib/node_modules/@deepseek-ai/dsh-client-ui-settings-general/lib/client.js`
- **C4（描述符一致）** `files/linux/.runtime-descriptor.json` 的 `runtimeId` 等于 APK
  `assets/runtime-descriptor.json` 的 `runtimeId`（build326 构建时打印的值）。

### 判定

- **通过**：S1 与 S2 的 A1–A5 全满足（A4 允许「不自动开始、用户手点一次」），B1–B3 无回归。
- **不通过**：维护页仍把「进入主界面」放主位；覆盖后直接进主界面看不到维护页；
  完成后「运行时版本与身份」仍显示「存在版本差异」。

真机回执请按[契约文档第「真机验收步骤」节](../overwrite-upgrade-and-maintenance.md)的字段
（上一版 → 本版、安装方式、旧 Web 是否存活、看到的页面、自动开始是否被拦、手点后是否成功、
Web / 插件结果、`runtimeId` 前后值）补写到本文第六节之后；设备截图与日志不进入仓库。
