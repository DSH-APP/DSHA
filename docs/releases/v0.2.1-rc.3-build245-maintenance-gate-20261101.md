## 2. 问题（源码核对，build244 仍存在）

- `EnvironmentMaintenance.recover()` 第一步 `ensureSingleRecovery` 直接逐域探测，任一域抛异常即以原始错误码失败；用户反馈的 3 次 `PLUGIN_JOURNAL_ID` 都发生在任何恢复动作之前。
- `PluginInstallJournals.blocked()` 把异常当作待恢复，转入 `PluginJournalRecovery` 后再次扫描、再次失败；`RecoveryRepairBroker` 又因门禁阻塞拒绝其他修复。
- 门禁 `Check` 只暴露 `blocked` 布尔，「有待恢复」与「读不了」没有调用方区分。
- 新旧数据根并存且无位置记录时，`UserDataLayout.selected()` 报 `DATA_LOCATION_AMBIGUOUS`，插件与启动配置两个域都读不了；`selectDataHome` 因门禁阻塞拒绝执行，而它正是这一状态的出口。单测已按此复现。

## 3. 改动（方案一：只给插件日志做隔离出口）

- `HostMaintenancePending`：`State`（CLEAR / PENDING / UNREADABLE）与稳定错误码 `code`；`inspectAll` 逐域检查且从不抛出（探测中的意外运行时异常同样记为 UNREADABLE）；原 `blocked` 语义不变。
- `recover()` 先做全域检查：有域读不了时抛 `MaintenanceUnreadable`，消息说明域、错误码与出口，不再执行必然失败的批量探测。
- `util/MaintenanceExitPolicy`：DATA_LOCATION_* → 选择数据目录；插件域且确有坏记录 → 隔离；其余域 → 只给诊断，不跳过可能半应用事务的回滚。
- `PluginInstallJournals.problems` 只读列出导致门禁或归档失败的具体记录（重复事务两侧都列出）；`PluginJournalQuarantine` 在屏障内重算并比对确认时的摘要，把记录原样移入 `plugin-install-quarantine/<批次>/entries/`，清单先以 moving 状态写入再逐条更新，完成后为 complete；不删除、不改写、不重放。隔离目录计入私有文档范围。
- 维护页：恢复前在后台计算隔离计划，有坏记录时改为原生确认隔离（列出至多 8 条路径与原因）；任务种类 `DSHA_ISOLATE_PLUGIN_JOURNALS_V1`。应急修复页与应急助手增加 `isolate-plugin-journals`；其源摘要绑定隔离计划，确认后计划变化即 `REPAIR_SOURCE_CHANGED`。
- `selectDataHome` 只被数据根以外的问题阻塞。
- 新增文案 11 条，覆盖十种语言。
