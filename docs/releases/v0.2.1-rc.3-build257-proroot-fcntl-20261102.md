## 2. 改动

- `tools/proroot-compat/stack-sysconf.c`：兼容层导出 `fcntl`。`F_DUPFD` / `F_DUPFD_CLOEXEC` 经 `RTLD_NEXT` 交给 vendor（保留其 dup 跟踪；找不到 vendor 符号时直接发系统调用而非退出），其余命令直接发内核系统调用，失败时按 glibc 语义设置 errno，成功不改 errno。vendor 自身 dup 失败仍是其 EPERM。
- `app/src/main/jniLibs/arm64-v8a/libdsha-proroot-compat.so`：NDK 26.3.11579264 锁定构建（Linux 主机产物仅 `.comment` 与 Windows 主机不同，按旧源码逐字节复现后以同法生成），`abi.lock.json`、运行时描述符、第三方声明同步更新。
- `tools/test-proroot-fcntl.py`：假 vendor 复现 v1.2.8 的 EPERM，代理在前时恢复 EAGAIN/EBADF/EINVAL、成功不改 errno、dup 仍转发 vendor；登记进 `host-tests.manifest.json`。

## 3. 检查

- 主机：`test-proroot-fcntl.py`（proroot guest 内 `qemu-aarch64`）通过；运行时描述符、源码卫生检查通过。本机无法运行 x86_64 NDK 工具，`build.py --check` 未在本轮重跑；rebase 未改动该二进制（sha256 `175f6b62…`），APK 内同一份。
- 真机（Lenovo TB321FU，Android 16，测试包 `io.github.sunsetrne.dsha.test` v256 构建自修复提交）：
  - 默认 proot：dsh Web 启动、鉴权并完成一轮对话；终端 bash 只映射 `libprootloader.so`，此时探针结果不代表修复。
  - 选 proroot 后重启：dsh Web 与新终端会话均在 `libproroot-bridge.so` 下，映射中有 `libproroot-runtime.so` 与 `libdsha-proroot-compat.so`；Web 完成一轮对话；新终端会话运行跨进程 `F_SETLK` 探针退出码 0（锁冲突返回 EAGAIN/EACCES；未修复时为 1，即 EPERM）。
