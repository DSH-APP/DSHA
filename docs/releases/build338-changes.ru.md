# DSHA 0.2.1-rc.5-20261108.0030-dsh0.2.2-rc.1 / build338

- Сохранение страницы K0–K2 (T110, `ba13ed5f` / `02e187e0`): когда хост-страница Web переключается на нативные настройки / терминал / страницу плагинов внутри той же задачи, документ WebView больше не уничтожается; при возврате та же страница принимается с тем же generation / instance, без повторного `loadUrl`. Новый `BrowserPageKeeper` поднимает владение страницей до области приложения, а `onDestroy` обрабатывает три ветви: смена конфигурации, обычное завершение и системное вытеснение. Остановка, обслуживание, смена процесса Web, выход renderer, origin-restore, удаление задачи и low-memory trim выполняют явный вывод из эксплуатации, поэтому реальная остановка не скрывается сохранением. K0 добавляет обезличенную диагностику `WEB_ENGINE` / `WEB_PAGE_DESTROY` / `WEB_KEEPALIVE_ATTACH|DETACH|RETIRE` (белый список кодов причин; URL, cookie и заголовки страниц не записываются).
- Внутренний переход в приложении больше не переподключается и не перерисовывает страницу целиком (T110 / сценарий K5 1, `b80d8225` / `7f13f06f`): при возврате в Web хост отправляет `dsha-browser-resume`, и управляемый `app-integration/client.js` сначала проверяет текущий carrier одним потоком `session.control` только для чтения. Если приходит любой кадр, Connection сохраняется и базовая линия Remote не перестраивается, поэтому длинная страница не перерисовывается целиком и не зависает на загрузке; если проверка истекла по таймауту, но Connection всё ещё `connected`, сброса также нет (действительно мёртвый carrier оставляется серверному heartbeat / socket close); при разорванном Connection или отсутствии возможности проверки поведение возвращается к прежнему. Новая обезличенная диагностика `WEB_PAGE_RESUME` записывает impl / trigger / state / probe / reset / hiddenMs / inApp для последующего разбора регрессий.
- Приёмка K5 на устройстве: сценарий 1 (длинная страница со стримингом, внутренний переход в приложении) пройден на LENOVO TB321FU / Android 16 / WebView 140 по фактическому тесту пользователя — повторное подключение «жёлтый → зелёный» исчезло, потоковый вывод больше не перезагружает страницу целиком и не зависает надолго, черновик сохраняется. Проверка выполнена на диагностическом тестовом пакете второго круга `3d3866f7` (то же исправление, что и в этом слиянии; пакет `io.github.sunsetrne.dsha.test`). Остальные сценарии (2–13: Home / переключение приложений, системное вытеснение, смерть процесса, поворот и тёмная тема / язык / шрифт, PiP, остановка / обслуживание / резервное копирование, origin-restore, renderer, многоконность, загрузка/выгрузка/микрофон, обезличивание логов) и второе устройство / второй WebView не выполнялись; по решению пользователя они объявлены экспериментальными и не блокируют слияние.
- Исправлено определение перекрытия на физическом экране (`bfe82527`): `MainScreenWindowPolicy` сначала собирает cover на display 0, которые выше цели по layer и пересекают её, затем единообразно вычисляет каждую грань по максимальному объёму обрезки, поэтому результат больше не зависит от порядка окон в списке и layer. Проверка примыкания для системного декора и IME получает допуск 2 px и правило «покрытие вдоль грани ≥ 80%»; примыкающие полосы / небольшие оверлеи, которых не хватает по покрытию, но которые уходят внутрь не более чем на 1/4 вертикального размера цели, обрезаются по этой грани. Внутреннее перекрытие по-прежнему отклоняет координаты для всего окна, новое состояние частичного перекрытия не вводится, а нулевые / обратные / null bounds пропускаются как геометрически не покрывающие пиксели (P2). Форма реального устройства ZUI (центральный taskbar плюс краевой игровой оверлей) переходит от полного отказа к обрезке; плавающий IME / разделённый экран / PiP и повторная проверка на ZUI/vivo не выполнялись.
- Следующий шаг в status виртуального экрана (T88, `850875bf`): отдельный `/app/vscreen/status` при отсутствии Core добавляет машиночитаемые `nextAction=CREATE_FIRST` и `retryable` (при ожидании очистки по-прежнему `ASK_USER_TO_CLOSE`) к `ok:false` + `VSCREEN_NOT_RUNNING`, сохраняя прежние поля error / state / lifecycle; `HttpShellService` и `VirtualScreenManager` — управляемые launcher-источники, поэтому descriptor пересчитывается по дереву слияния (runtimeId `a77aa93f…`).
- Вторая партия UI (остаток T114 + ошибки и составные состояния ⑬, `61245640`): на странице восстановления запуска строка действий оставляет только заголовок действия, описание эффекта уходит в ⓘ в конце строки, причина недоступности остаётся в строке, описание группы переносится в ⓘ рядом с заголовком, перестроенные списки восстанавливают позицию прокрутки и появляются с затуханием, баннеры результата переходят при появлении / смене текста. Страница установки плавно показывает заключение / состояние / прогресс, секундомер меняет только цифры без мигания, шесть этапов подсвечиваются при смене, ошибки обслуживания по базовой линии UI ⑬ сводятся к короткому заключению + ⓘ с сохранением семантического цвета ошибки. Страница диагностики перекрёстно затухает заключение / состояние / кнопки и подсвечивает ступени значков; полоса этапов обслуживания перестраивается только при смене формы этапа; предупреждение root и капсулы обзора разрешений устройства появляются с затуханием, цветные точки подсвечиваются; карточки состояния страницы данных плавно показывают заключение, а пути и детали нативных задач переходят в ⓘ; страница передач возвращает список обратным сдвигом за 160 мс; WebPreview / WebCrashPanel плавно показывает верхнюю полосу прогресса и панель ошибки за 180 мс. В `UiMotion` добавлены `crossFadeTimerText` / `flash` / `reveal`, в `InfoHint` — `bindOnSurface`, добавлен `StartupRecoveryLayoutTest` и расширены наборы UiMotion / InfoHint; новая строка «Показать описание:» внесена в messages-extra с восемью переводами.
