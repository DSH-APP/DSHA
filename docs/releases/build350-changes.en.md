# DSHA 0.2.1-rc.5-20261109.2300-dsh0.2.2-rc.1 / build350

- Minimal window evidence and actionable multi-window hints for the virtual screen (T98, `33ceab2c7`): the split `FRAME_NOT_READY` replies from `see` and the window-unavailable replies from tree / node / editor / anchor now carry a minimal read-only window snapshot when accessibility can read windows (`util/VirtualScreenWindowEvidence`): application / system / input-method window counts, `focusedWindowId` / `activeWindowId`, `windowAmbiguous`, and — only when a single window is selectable — the target window's displayId / id / type / layer / bounds / focused / active / title / package. Titles drop control characters, collapse whitespace and are truncated to 64 code points; packages are kept only after package-name validation and every other invalid value is omitted. The snapshot contains no node text, control content, screenshots or full window list. `NO_UNIQUE_APPLICATION_WINDOW` now distinguishes two causes by counts: several application windows side by side (split screen / floating window) → `reason=VSCREEN_WINDOW_AMBIGUOUS`, `nextAction=ASK_USER_TO_CLOSE_SPLIT_SCREEN`; only system / input-method windows and no application window → `reason=VSCREEN_NO_WINDOW`, `nextAction=LAUNCH_APP_FIRST`. Evidence only explains the failure and the next step and **never takes part in authorization, window selection or retries**: the semantic path still accepts only the unique result of `VirtualScreenWindowPolicy.selectDetailed`, and the anchor path still accepts only the windowId carried by the original observation (a repeated id is still rejected as `ANCHOR_WINDOW_AMBIGUOUS`); a "multi-window" situation never silently switches to another window.
- Sensitive-screen tiers and handoff for the virtual screen (T119, `dc6f9642e` / `c3a4e3c30` / `241e06159`): new `util/SensitiveScreenClassifier` and `util/SensitiveScreenPolicy` (pure logic) add a conservative whole-screen classification on top of the 6.1 password-focus hard guard (password / one-time code / payment / system security / sensitive but unreadable `SECURE_UNKNOWN`), defaulting to `ASK` for every category; each category can be set to `HANDOFF` — pause the assistant before dispatching any input, revoke in-flight requests and discard observations, returning `ok:false` / `state=NOT_SENT` / `error=SENSITIVE_SCREEN_HANDOFF` / `sensitivity=<category>` / `readOnly:true` / `retryable:false` / `nextAction=HANDOFF_TO_USER`; after the user resumes, the assistant must `see` again and never replays automatically. `OFF` only disables whole-screen tiers and returns to the ordinary confirmation policy. Password text read/write stays hard-blocked at the input layer and is not lifted by any tier or confirmation. `ALLOW_ALL` and per-app `ALLOW` only skip ordinary confirmations and cannot bypass a sensitive `ASK`; a sensitive confirmation is one-shot and **is not written into the "allow this app this turn" 5-use memory** (ordinary apps still re-ask every 5 uses). Settings → Device capability grants → Screen observation gains a separate "Sensitive screen handoff" row with per-category ask / handoff and two exact-package lists (forced handoff and trusted apps; empty by default, at most 64 each, mutually exclusive, corrupt data falls back to ASK). The screen `policyRevision` combines the `screen_confirmation_v1` and `sensitive_screen_v1` revisions, so any save invalidates old confirmations and in-flight requests, with a monotonic lower bound inside the process; endpoints that inject input re-classify after confirmation and before dispatch — an unreadable screen returns `SENSITIVE_SCREEN_UNVERIFIED` and a changed category returns `SENSITIVE_SCREEN_CHANGED`, both unsent and retryable by observing again.
- Island (notification pill) fixes (PR #12, `ccd4b81d7`, already in main): the expanded view keeps a single turn indicator (notification subText), the body no longer repeats "Turn N", and no per-second elapsed value is written while running, so the content signature stays stable and heartbeat rebuilds no longer swallow option-button taps; background answer failures must be visible — an HTTP non-200, empty submit, expired options or a dead entry shows a Toast (with the HTTP status and server error code, e.g. `HTTP 409 NO_WAITING`) and points the user back into the chat, while the app log records `TASK_ANSWER_REJECTED <status> <body>`; opening the chat from a notification now checks whether the question card actually has an option row (`Mbwy4a_optionRow`) — the `Mbwy4a_options` container renders for every card and would always be true — and with options present it does not steal focus, keeping the keyboard down so the card's bottom "Submit" is not pushed out of view. `docs/island-status.md` now carries a platform verification table: native Android 16, 16 QPR1+, HyperOS, ColorOS 16 and OriginOS 6/7 are marked row by row (per-platform branch support / code support not on hardware / contributor device observation, not committed / public information not on hardware / expected support with no on-device record), and OriginOS 7 (Android 17) is explicitly listed as having no repository record of an on-device run.
- Managed runtime update: the T98 / T119 changes touch `runtime-descriptor` launcherSources, and the merged tree recomputes `runtimeId` to **`5ff08d58`** (`b6220b227` registers the new T98 Java file, `084b692f2` recomputes); fixed inputs stay frozen at the locked 20261105e and the bundled `dsh-web-mobile` stays upstream 3.3.1 and default-enabled.
- Version and scope: versionCode raised to 350 (based on the released build349 / `3264f7868`); the DSHA revision stays `0.2.1-rc.5` with bundled DSH `0.2.2-rc.1`. This batch contains the two virtual-screen policy lines T98 / T119 and the already-merged PR #12; it does not relax the device shell allowlist or execution-time guards, and the password text hard block and fail-closed authorization semantics are unchanged. build349 is already released as a formal package (tag `dsha-a-su-build349-20261109-140000`).
- **Not verified / not accepted**: no device acceptance yet: for T98, multi-window / split screen should ask the user to close split screen instead of auto-selecting a window, IME windows only enter `inputMethodWindowCount`, and `FLAG_SECURE` pages still expose metadata-only window evidence when capture fails; for T119, the ASK / HANDOFF / OFF tiers, the forced-handoff and trusted-app lists in both directions, sensitive confirmations not entering the 5-use memory, the pause on HANDOFF and the mandatory re-observe after resume, the settings page scrolling on short screens / at 1.3× font, and the degradation when accessibility is off (protection degrades, no security claim); for PR #12, the single turn indicator / visible failures / no focus stealing with options on real ROMs, plus the OriginOS 7 island (no on-device record yet). **build350 is not yet device-validated**: acceptance is a first 349→350 overwrite that succeeds, data intact, READY, the managed-runtime update and the behaviours above on device; build344–build350 formal-package overwrite acceptance is still pending with the user, and device acceptance of the released build338–build349 follows their own records.
