# DSHA 0.2.1-rc.5-20261106.2228-dsh0.2.2-rc.1 / build334

- P0 исправление обновления поверх (T91, `a70232fc`): после установки build333 поверх на реальном устройстве proroot-лаунчер мог завершаться поздно или оставаться после выхода пробного guest (наблюдалось на OnePlus PJD110 / Android 16 / WebView 156, в том числе без других Web-процессов в фоне); шаг завершения `RuntimeTrial` ошибочно считал «объект лаунчера ещё жив» провалом пробы `TRIAL_PROCESS_UNCONFIRMED`, из-за чего транзакция обновления рантайма оставалась полузафиксированной (`files-committed` / `settings-committed`), запуск блокировался барьером обслуживания, и перезапуск не помогал. Теперь завершение пробы подтверждается только доказательством выхода guest из этой записи, а остаточный лаунчер больше не меняет вывод. `RuntimeTrial` выполняет одну ограниченную очистку удерживаемого `Process` для этого экземпляра; тайм-аут или ошибка лишь пишут диагностику `TRIAL_LAUNCHER_RETENTION`. Для записей `launched` без доказательств `.dsha-web.pid` / `.stale` `TrialRecovery` теперь требует, чтобы платформа подтвердила отсутствие такого процесса в производном профиле пробы (тот же UID, два совпадающих рождения); если процесс существует, недоступен для чтения или идентичность изменилась — по-прежнему fail-closed, и неисправимый пробел в доказательствах больше не остаётся.
- Диагностика сбоев обслуживания и очистка устаревшего сбоя: начало и сбой задачи обслуживания теперь пишут экспортируемые записи операций (`MAINTENANCE_TASK_START` / `MAINTENANCE_TASK_FAILED`), а в состоянии сбоя остаются доступными аварийный DSH, записи обслуживания, экспортируемая читаемая копия и «войти в ограниченный главный интерфейс». После внешнего восстановления, как только среда работоспособна и нет выполняющегося или ожидающего обслуживания, страница отбрасывает устаревший снимок сбоя (`RuntimeUpgradeState.clearStaleFailure`), возвращается к стандартному состоянию «предыдущий рантайм ждёт обновления» с точкой входа обновления и больше не просит нажать «повторить» ещё раз. Журнал запуска помечает «ссылка аутентификации получена, но итоговый ready / failed не записан» как «готово · ожидание входа» вместо «прервано · нет результата».
- Обновление поверх выводит из эксплуатации предыдущую версию (I10): только когда идентичность установленного APK отличается от записанной идентичности сеанса, путь обслуживания / принудительной остановки дважды проверяет записанную идентичность рождения (boot, PID, время рождения, командная строка, UID, поколение/экземпляр/nonce), затем сначала останавливает записанный guest, а затем соответствующий старый proot-лаунчер (SIGTERM → короткое ожидание → повторная проверка → SIGKILL). Если выход guest не подтверждён, лаунчер не трогается; при любом провале проверки, нечитаемой среде, повторном использовании PID, чужом UID или изменении между двумя наблюдениями сигнал не отправляется, а исходная среда сохраняется. Обычная остановка, текущий экземпляр, терминалы, виртуальный экран и путь изолированной пробы не меняются (I9). Диалог принудительной остановки явно указывает «отказаться от предыдущего Web и принудительно остановить» и порядок guest → старый лаунчер.
- Инцидент build333 и статус приёмки: 2026-11-06 после установки build333 поверх build332 на OnePlus PJD110 (Android 16, WebView 156) возникла описанная полуфиксация (транзакция `69ebb4f7…`); запуск был заблокирован, перезапуск не помогал.
