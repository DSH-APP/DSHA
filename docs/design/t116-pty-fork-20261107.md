# T116 终端错误「pty.fork is not a function」审计（2026-11-07）

> 审计对象：DSH Web 会话侧栏「终端」标签打开即报 `终端错误：pty.fork is not a function`（重试必现）。
> 审计方式：只读。未改产品代码、未安装、未重启 Web/App、未操作手机。
> 结论一句话：**不是 node-pty 版本/ABI 坏了，而是同一 Node 进程里 `sharp` 的原生模块先于 `node-pty` 加载，导致 `node-pty` 的 `pty.node` 初始化到了 sharp 的导出对象上**；`pty.fork` 因此不存在。build336 更新本身没有改这些包，它带来的是 **Web 进程重启**，重启后「先显示/发送图片 → 后打开终端」的顺序把这个潜伏缺陷暴露出来。

## 1. 结论

1. `pty.fork is not a function` 由 `node-pty` 自己的 `lib/unixTerminal.js:94` 抛出（`pty` = `loadNativeModule('pty').module`，即 `prebuilds/linux-arm64/pty.node` 的导出对象）。
2. 运行中的 DSH Web 宿主进程（pid 32455，Node v24.19.0）里，`require.cache` 中 `.../node-pty/prebuilds/linux-arm64/pty.node` 的导出 **不是** `fork,open,resize,process`，而是 sharp 的 N-API 导出：`metadata,pipeline,cache,concurrency,counters,simd,libvipsVersion,format,block,_maxColourDistance,_isUsingJemalloc,_isUsingX64V2,stats`。在宿主进程内对同一路径重新 `process.dlopen` 也得到 sharp 的导出。
3. 磁盘上的 `pty.node` 字节是**正确**的（sha256 `5a3b8930d625…`，69112 B，含 `PtyFork/forkpty` 符号）；同一字节在**新进程**里加载得到 `fork` 函数，`node -e` 实际 `spawn` 一个 bash 成功。
4. 最小复现：新进程里先 `require('sharp')`、再 `require('node-pty')`，`pty.native.fork === undefined`，`pty.spawn(...)` 抛出的正是 `pty.fork is not a function`；反过来先 `node-pty` 后 `sharp` 则一切正常，且之后再加载 sharp 也不会破坏已加载的 node-pty。
5. 宿主里是什么先加载了 sharp：`@deepseek-ai/dsh-attachment-local` 是宿主里唯一使用 sharp 的包；Web 端渲染任何图片附件都会走 `sessions.attachment` → `attachments.readImage` → `probeImage` → `requireSharp()`。本进程 22:31:54 UTC 启动，23:04:11 UTC 写入第一张图片附件（WebP），23:10 左右第一次打开终端即报错。
6. 与 build336 的关系：`tools/dsh-runtime/package-lock.json` 在 build330 / build336 两个 tag 上 **diff 为空**（同为 DSH 0.2.2-rc.1、node-pty 1.2.0-beta.15）；`pty.node` 与 sharp 二进制在 0.2.1-rc.5 / 0.2.2-rc.1 / 当前已装 runtime 三处 **sha256 完全相同**；proroot 固定输入在两个 tag 之间也没有变更。所以**不是 build336 换包或换原生绑定引入**，而是进程重启 + 加载顺序触发的潜伏缺陷。用户「之前版本没问题」与「旧进程里终端先被加载过，因此免疫」一致。

## 3. 证据

### 3.1 在运行中的宿主进程里复现（同一错误、同一进程）

本次审计会话的宿主就是出问题的 Web 宿主（pid 32455）。调用工具终端：

```
terminal_open(type="shell") → Error: pty.fork is not a function
```

说明错误发生在**当前 Web 宿主进程内部**，不是浏览器端、也不是 App 原生终端（Temux JNI）。

### 3.2 宿主进程内的模块状态（Node inspector，只读表达式）

通过宿主自带的 inspector（`http://127.0.0.1:9230/json/list`，target `DeepSeek Harness Host`）在 pid 32455 内取值：

```js
const r = process.getBuiltinModule("node:module")
  .createRequire("/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-subprocess-local/lib/index.js");
r.resolve("node-pty")            // /usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/node-pty/lib/index.js
Object.keys(r("node-pty"))       // native,spawn,fork,createTerminal,open
typeof r("node-pty").native.fork // undefined（异常）
Object.keys(r("node-pty").native)
// metadata,pipeline,cache,concurrency,counters,simd,libvipsVersion,format,block,
// _maxColourDistance,_isUsingJemalloc,_isUsingX64V2,stats   ← 这是 sharp/libvips 的导出
```

`require.cache` 里 `.../prebuilds/linux-arm64/pty.node` 的 `filename` 与缓存键都正确，但 `exports` 就是上面这组 sharp 键。宿主进程里对同一路径执行 `process.dlopen(新 Module, pty.node)` 仍返回 sharp 键（不是缓存键的问题，是**加载/初始化**这一步走错）。

宿主进程内 `fs.readFileSync(pty.node)` 的 sha256 为 `5a3b8930d62535edabec2eac79fe8eca70a178d93fbb76b1ae875dd60ee8f825`、69112 B，与磁盘一致；`/proc/32455/maps` 映射的 inode 也是当前文件。即**文件本身没坏，宿主也读到了正确字节**。

### 3.3 最小复现与顺序矩阵（新进程，不碰运行环境）

```bash
cd /usr/local/lib/node_modules/@deepseek-ai/dsh
node -e '
const sharp = require("sharp");
const pty = require("node-pty");
console.log(typeof pty.native.fork);        // undefined
pty.spawn("/bin/bash", ["--norc","-i"], {cols:80,rows:24,cwd:"/root",env:process.env});
'   # → TypeError: pty.fork is not a function
```

顺序矩阵（都在独立新进程，二进制相同）：

| 顺序 | 结果 |
|---|---|
| `sharp` → `node-pty` | `pty.native.fork === undefined`，`spawn` 抛 `pty.fork is not a function` ✗ |
| `node-pty` → `sharp` | 各用各的导出，`spawn` 正常 ✓ |
| `node-pty` → `node-pty` 副本 | 正常 ✓ |
| `sharp` → `node-addon-require-builtin` / `node-addon-system` / `koffi` | 各自正常 ✓ |
| `sharp` → `pty.node` 的 `/tmp` 副本 | 仍得到 sharp 键 ✗（不是路径/文件名问题） |
| `node-pty` → 之后再 `sharp` | node-pty 不受影响 ✓（**一旦先加载过 node-pty，本进程就免疫**） |

结论：这是 **N-API 原生模块的加载顺序/符号互串**（`napi_register_module_v1` 一类全局注册符号被先加载的 sharp 顶替），只影响 `pty.node` 这一个组合；二进制、ABI、路径都不是原因。

### 3.4 版本与二进制一致性（为什么不是 build336 换包）

| 检查 | 结果 |
|---|---|
| `git diff build330..build336 -- tools/dsh-runtime/` | 空（lock 完全一致；两边都是 DSH 0.2.2-rc.1 / node-pty 1.2.0-beta.15） |
| `pty.node` sha256：0.2.1-rc.5 归档 / 0.2.2-rc.1 归档 / 当前已装 runtime | 三处均为 `5a3b8930d625…`（69112 B） |
| `sharp-linux-arm64-0.35.5.node` sha256：旧/新/已装 | 三处均为 `6c3c549bd1ba…` |
| `git diff build330..build336 -- tools/ci-build-inputs.lock.json docs/fixed-build-inputs.md app/src/main/jniLibs` | 空；`jniLibs/arm64-v8a` 内含 `libproroot-*.so` / `libdsha-proroot-*.so`，即 proroot 二进制两版相同（`docs/runtime-engines.md:141` 也记录 build330 已是 proroot v1.2.8） |
| `@deepseek-ai/dsh-attachment-local` 旧 0.2.1-rc.5 vs 现 0.2.2-rc.1 | `requireSharp`/`probeImage`/`detectImage` 逻辑相同（仅行号偏移 2 行） |

因此 **不存在「build336 把 node-pty 换成了缺 fork 的版本」这种情况**；回退 build330、重打 runtime 都不会改变二进制。

### 3.5 本进程时间线（触发顺序）

| UTC | 事件 | 证据 |
|---|---|---|
| 22:31:54 | build336 更新后 Web 宿主重启（新进程，`DSHA_WEB_GENERATION=2`） | `process.uptime()` / inspector |
| 23:04:11 | 本进程**第一张图片附件**写入（WebP，77 KB）→ `dsh-attachment-local` 校验图片 → `requireSharp()` → sharp 原生模块加载 | `/root/.dsh/attachments/v1/objects/a1/a1d4f89c…` mtime；该目录在 22:31 后只有这一张早于报错的图片 |
| ~23:10–23:14 | 第一次打开 Web 侧栏终端 → `require('node-pty')` → `pty.node` 初始化到 sharp 导出 → `pty.fork is not a function`；重试仍失败（模块已缓存） | 用户报告、截图文案 `dsh-client-ui-sidebar-terminal` client.js:305 |
| 23:17/23:19 | 用户补发的错误截图（WebP） | 同目录另外 3 个 RIFF 对象 |

图片 → sharp 的路径（宿主侧，已核对源码）：Web 端显示/发送图片会走 `@deepseek-ai/dsh-api-session-controller` 的 `attachment()`（lib/index.js:886）→ `ctx.attachments.readImage`（`dsh-attachment-local/lib/index.js:1041`）→ `readImageFile` → `probeImage`（:169）→ `requireSharp()`（:120）。所以**重启后只要看过任意一张图（会话历史里的截图也算），之后第一次开终端必中**；这也解释了「重试无效、换标签无效」。

## 4. 引入时间点判断

- **缺陷本身**：至少 0.2.1-rc.5 起就存在（同样的 node-pty / sharp 二进制、同样的附件 sharp 逻辑），属于潜伏的**进程内原生模块加载顺序**缺陷，没有找到某次提交把它「改坏」。
- **本次可见的触发点**：build336 覆盖安装导致 **Web 进程重启**（22:31:54）。旧进程长时间运行，终端早在某次使用中先加载过 node-pty（或先于图片），因此免疫；新进程里顺序反了。
- **build336 相关的放大因素（推测，未做 A/B）**：build336 起内置 `dsh-web-mobile` 3.3.1 默认启用（T101），移动端图片/截图附件交互更频繁，重启后「先看图再开终端」的概率显著升高；但这不是代码层面的因果，`tools/dsh-runtime` 与附件实现均未变。
- 因此报告结论是：**环境更新（重启）是暴露条件，不是根因**；只要进程里 sharp 先于 node-pty 加载，任何版本（含 build330、build337 候选）都会复现。

## 5. 修复方案

### 5.1 推荐（最小、可随 build337 出包）

在 DSHA 自有的启动预加载里（`app/src/main/assets/startup-observer.cjs`，部署为 `/root/.dsh/startup-observer.cjs`，由 `NODE_OPTIONS=--import=…` 在 DSH 应用启动前执行）**先把 node-pty 的原生模块加载并缓存**，让后续任何 sharp 加载都抢不到前面：

```js
// T116：sharp（附件图片）若先于 node-pty 加载，pty.node 会注册成 sharp 的导出，
// 终端随后抛 pty.fork is not a function。这里在插件加载前固定 node-pty。
try { requireFrom(path.join(installation, 'package.json'))('node-pty'); } catch (_) { }
```

位置建议：`const installation = …`（当前第 31 行）与 `function requireFrom(…)`（第 39 行）之后、插件扫描之前。失败必须静默（`try/catch`），不影响启动。

验证（已在同构新进程做过）：

```bash
node -e '
  require("/tmp/pty-preload.cjs");            // 内含 require("node-pty")
  require("/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/sharp");
  const pty = require("/usr/local/lib/node_modules/@deepseek-ai/dsh/node_modules/node-pty");
  console.log(typeof pty.native.fork);        // function
  const t = pty.spawn("/bin/bash",["--norc","-i"],{cols:80,rows:24,cwd:"/root",env:process.env});
  // 实际输入 echo FIX_OK_$((2+2)) → 输出 FIX_OK_4，SPAWN_OK
'
```

好处：不碰上游 DSH 包、不重打 runtime、不依赖附件插件顺序；节点只是一次 ~69 KB 的 dlopen。风险：启动多映射一个 .node；若 node-pty 缺失/损坏，`catch` 后行为与现在一致（终端仍报错，但启动不受影响）。

### 5.2 立即缓解（不重装、不改包）

1. **停止/启动 Web**（重置宿主进程），然后在**发送/查看任何图片之前**先打开一次终端标签；此后本进程内再处理图片也不会坏。
2. 或者热修部署副本 `/root/.dsh/startup-observer.cjs` 加上 5.1 的两行，再停止/启动 Web。注意：该文件属于受管 runtime 布局，APK 覆盖更新/修复时会被 `app/src/main/assets/startup-observer.cjs` 覆盖，所以只适合临时验证；正式修复仍应进仓库随 build337 出包。

### 5.3 不建议

- **回退 build330 / 重打 dsh-runtime.bin**：二进制完全相同（见 3.4），无效。
- **换 node-pty 版本**：0.2.1-rc.5 与 0.2.2-rc.1 都是 1.2.0-beta.15，问题在加载顺序，不在版本。
- **在跑着的进程里删 `require.cache` 重载**：需要改活动进程状态，且 sharp 已加载，重载仍会拿到错误注册，不稳定。
- **改 `dsh-attachment-local` 去掉读路径的 sharp 复检**：上游代码，且会改变附件完整校验语义，不适合作为本次热修。

### 5.4 上游建议（不阻塞本次）

向 DSH 上游反馈：宿主启动时预加载 node-pty，或让 `dsh-attachment-local` 的读路径不再用 sharp 做二次元数据探测（ingest 已校验过），并用一个「先 sharp 后 node-pty」的冒烟用例守住回归。
