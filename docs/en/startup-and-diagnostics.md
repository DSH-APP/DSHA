## Startup gates and states

| Entry / state | Behavior | Failure or limit |
|---|---|---|
| Welcome not completed | Main and the recovery workbench first open Welcome, then environment preparation | “Skip introduction” still opens preparation; it does not bypass the environment contract |
| Environment not ready or maintenance unfinished | Main opens installation/maintenance | An explicit limited entry can show native tools; limited entry does not mean Web works |
| First preparation completed | Display Main, then asynchronously submit one normal Web start | Manual Start/Stop supersedes a queued first request; rotation does not resubmit it |
| Web starting | The current generation records stages, a timeline, and plugin observations | The 60-second notice is not a kill deadline; slow startup, timeout, or unknown execution does not replay business operations |
| Backend auth URL captured | Backend output supplies the current local service URL and authentication data | It does not prove the browser bundle, plugins, or page are ready |
| Browser ready | The current page observer reports ready and records startup state | Unused plugins, external models, and all device capabilities remain unproven |

Entry points are [MainActivity](../../app/src/main/java/com/deepseekharness/app/ui/MainActivity.java), [WelcomeActivity](../../app/src/main/java/com/deepseekharness/app/ui/WelcomeActivity.java), and [FirstRunWebStart](../../app/src/main/java/com/deepseekharness/app/ui/FirstRunWebStart.java). [StartupPipeline](../../app/src/main/java/com/deepseekharness/app/core/StartupPipeline.java) prepares normal startup; [StartupDiagnostics](../../app/src/main/java/com/deepseekharness/app/core/StartupDiagnostics.java) combines backend and page observations. Page events still validate host, generation, current same-origin document, nonce, and sequence through [StartupPageGate](../../app/src/main/java/com/deepseekharness/app/util/StartupPageGate.java). A nonce is not isolation between scripts of the same origin.

Stop and restart must follow real process identity and exit barriers, never force-killing by port, name, or bare PID. See [runtime engines](runtime-engines.md) for the narrow fallback after explicit pre-authentication proroot failure. Slow startup and plugin errors do not authorize changing engines to replay work.

## Host recreation and the first-use Web notice

When the host process is recreated, [StoredWebSession](../../app/src/main/java/com/deepseekharness/app/runtime/StoredWebSession.java) supplies an encrypted local record in noBackup. [WebSessionRecovery](../../app/src/main/java/com/deepseekharness/app/core/WebSessionRecovery.java) identifies the same already-live Web in read-only fashion. Adoption requires compatible APK/descriptor/root, matching boot/PID birth/UID/command and environment-generation instance nonce, successful real HTTP authentication, and another process check before adoption. It creates no new Web and restores or replays no old task.

After the second kernel-identity check and strict adoption, [WebLifecycleController.publishRecoveredLan](../../app/src/main/java/com/deepseekharness/app/core/WebLifecycleController.java) hands the cookie from that strict verification to [LanAuthBridge.publishVerified](../../app/src/main/java/com/deepseekharness/app/core/LanAuthBridge.java). Publication rechecks the current generation, complete URL, and actual port. It performs no second HTTP exchange and does not rerun `afterAuthenticated` startup tasks. LAN does not listen when disabled. A LAN-bind failure records a warning without undoing adoption of the verified Web. See [ports and networking](ports-and-networking.md) for the full LAN switch and authentication boundaries.

A missing record with an old PID, incompatible evidence, failed authentication, or unreadable identity conservatively becomes UNKNOWN and retains the barrier. Normal cold startup with neither a record nor an old PID is unaffected. Host reclamation by the system does not imply guest exit, and UNKNOWN must not trigger automatic extraction/rebuild. Related regressions are [WebSessionProofTest](../../app/src/test/java/com/deepseekharness/app/util/WebSessionProofTest.java) and [WebSessionRecoveryTest](../../app/src/test/java/com/deepseekharness/app/core/WebSessionRecoveryTest.java); these do not prove real-ROM background recovery.

[MainEntryGate](../../app/src/main/java/com/deepseekharness/app/ui/MainEntryGate.java) checks Main's environment gate in the background. Pause, destroy, a new Intent, or a new generation invalidates an old delivery ticket; slow disk does not obtain navigation authority. Waiting to enter the current authenticated Web has a visible 15-second completion boundary, and an old result must not navigate a new page. Failure of that UI wait does not prove backend exit and must not start a second backend automatically. See [MainEntryGateTest](../../app/src/test/java/com/deepseekharness/app/ui/MainEntryGateTest.java).

### Background rechecks, UNKNOWN, and retaining the original page

F13 software negative controls using the actual compiled F12 classes reproduced two behaviors: one failed background identity check permanently left `restoreUnknown` set even after later evidence recovered, with the old registration already revoked; a normal new start also entered periodic rechecks after saving its record, so this was not limited to host reconstruction. Old logic then interpreted an absent ready/auth result as Web closure, affecting service protection and the preview. This is a demonstrated software path, not the sole proven cause of the phone's background event or ROM restrictions.

| Process observation and current identity | Page, authority, and next step |
|---|---|
| `LIVE` with a continuously valid current identity | Retain the verified run and original page without starting another backend |
| `UNKNOWN`, temporary read denial, or unproved authentication | Retain the original DOM or Gecko session and this run's background protection, showing verification state; revoke screen epoch, old task tickets, and LAN, without treating display identity as ready authority |
| Confirmed guest `EXITED` | Show that the backend exited and preserve records/diagnostics; launcher exit is separate evidence and the stop barrier is not cleared by this alone |
| Changed generation, instance, record, URL, or port | Discard the old asynchronous result; do not update a new page, revive old grants, or publish old LAN state |

[WebSessionRecheck](../../app/src/main/java/com/deepseekharness/app/core/WebSessionRecheck.java) and the [lifecycle controller](../../app/src/main/java/com/deepseekharness/app/core/WebLifecycleController.java) coalesce foreground/background checks asynchronously, without proc reads or HTTP waits on the UI thread. Recovery from UNKNOWN requires the same record/generation/instance/actual port/auth URL, a fresh kernel observation, actual HTTP authentication, and a second kernel observation. Only then is a new `AgentTaskRegistration` object created and the original page notified to continue. It uses the record's existing taskToken/nonce. The old registration remains permanently revoked and old rows/queued tickets do not revive. Conversations, stop tickets, backend starts, and dispatched business work are not resubmitted.

Standard's [WebPreviewActivity](../../app/src/main/java/com/deepseekharness/app/ui/WebPreviewActivity.java) and Low's [GeckoPreviewActivity](../../app/src/low/java/com/deepseekharness/app/ui/GeckoPreviewActivity.java) retain the original page/session for same-identity verification rather than treating null ready as an ended instance. UNKNOWN places a full native status panel over the page and disables WebView interaction or Gecko's active state. Native file, microphone, IME, and similar entries still require strict ready identity. Display identity retains a page only; it grants no additional authority and does not promise to freeze all JS, backend RPC, or Node business work. Existing legitimate backend work is neither killed nor replayed. Targeted JVM/Robolectric positive controls and negative controls using the compiled F12 classes are complete. Actual Standard Activity onCreate/GEN routing/newIntent, repeated same-DOM recovery, a new Blob writer, and Service WakeLock were checked in Robo fixtures. Low was compiled and source-reviewed only, without a complete Gecko Activity regression. The delivery owner separately runs full dual-flavor Gradle and final-APK checks. Real background protection, the reported phone, accounts/models, and device coverage require their own tests; this page does not claim the phone fault has disappeared.

Backend authentication and page mounting remain separate. If the startup observer is injected late, or the first-use notice/empty session has no composer yet, mounting is confirmed only by the locked rc2 layout's `shell-bottom` and `shell-overlay` combination; an arbitrary nonempty root is insufficient. The first-use notice closes only after a real view from the official Host configuration confirms that the exact `welcomeNoticeVersion` is persisted. A click, a returned mutate call, or any nonempty value is insufficient.

The F12 real-Host negative controls on both browser engines cover an early failure response, a later background save that previously left the page showing an error, and revision conflict. These are software behavior records, not evidence of a particular Host error code from a phone screenshot. This page did not rerun the controls; the [F12 record](releases/v0.2.1-rc.2-build190-fix12-20261021.md) binds the original objects and execution results. [WelcomeNoticeStore](../../tools/welcome-notice/WelcomeNoticeStore.js) uses the official shared mirror's `ensure/load` to verify through Host describe, with at most eight seconds for each UI read wait. Expiry does not cancel a submitted Host write. Unknown responses or exceptions trigger bounded read-back rather than automatic resubmission. Unsaved state remains an error instead of becoming an invented acknowledgment. After automatic failure, the same mirror remains observed so a later exact persisted confirmation can close the notice. Explicit return to the notice, session-only entry, or page disposal detaches the old wait; session-only entry applies only to that session.

Only an explicit refusal followed by an official recovery read showing a changed revision, while still ready and writable, permits a limited retry of the same acknowledgment field, with at most two write attempts. Unknown transport results do not enter that branch. If Host persisted and broadcast before the original mutate reply, the confirmed mirror may be consumed; a late rejection does not erase it. Pushes for other fields cannot reset saving or invent success. Mounting code is in [startup.js](../../app/src/main/assets/web-integration/startup.js); the regression entry is [test-welcome-notice.mjs](../../tools/test-welcome-notice.mjs). These mechanisms do not establish phone, real-account, or model acceptance.

## Diagnose an unavailable workspace directory service by layer

When `directoryPicker/list` returns `gateway/service-unavailable` and `active Service directoryPickerController unavailable`, check whether the actual Remote service is active. A mounted page, visible directory UI, or reachable Web port does not prove that service is ready. F13's actual-Host negative control confirmed that disabling `workspaceRegistry` leaves the original `WorkspaceController` waiting for its static dependency and its constructor's directory child unregistered, even with the browsing backend/UI active. Healthy raw/managed empty profiles already worked. Why the phone registry was not ready remains unknown; a screenshot alone does not establish corrupt history, automatic ports, or missing core services generally.

The [directory service patch](../../app/src/main/assets/directory-picker-service-patch.json) composes the actual `DirectoryPickerController` independently from the original workspace controller, retaining backend dependencies, Gateway authentication, parameter/path checks, and original named-class behavior. Completed directory-specific Host controls cover actual list/create/readback with registry disabled while preserving the fixture's original file, path/authentication/missing-backend rejection, healthy workspace saving, and two normal same-profile shutdown/reopen cycles. Corrupt records and HMR are not counted as passed directory coverage. This is isolated host-software evidence, not phone-picker acceptance. See [plugin operations](plugins.md) and [runtime/data/plugin mechanisms](runtime-data-plugin-architecture.md) for the contract and workspace-retention rules.

A directory-service error does not trigger clearing Ubuntu, deleting sessions, rebuilding external workspaces, or replaying unknown writes. Preserve current data and redacted errors, then diagnose through normal startup/maintenance and exit barriers. Android's system file picker, native-backup SAF permission, and this Web service are separate; none proves another has been repaired.

## Native recovery workbench

[StartupRecoveryActivity](../../app/src/main/java/com/deepseekharness/app/ui/StartupRecoveryActivity.java) works when Web cannot load. It offers recent startup records, configuration snapshots, plugin checks, and these actions.

| Action | When it takes effect | Boundary |
|---|---|---|
| Retry startup | Requests one normal recovery start after environment readiness and no pending configuration repair | Does not bypass maintenance/process gates or promise automatic resumption of failed work |
| Start the basic interface in safe mode | This invocation uses an independent basic configuration | Keeps original plugins/configuration; safe startup is not OS sandbox isolation of third-party code |
| Create configuration file | After selecting Web/settings/patch and confirming | Stops Web/terminals, saves pre-repair configuration, then replaces the chosen target |
| Recover interrupted configuration repair | After explicit confirmation, handles the owning transaction | A page-read failure is not replayed as a write repair |
| Environment repair / compatible runtime rollback | Executes after entering the plan and maintenance chain | Stop barriers, trials, compatibility checks, and in-place personal-data contracts still apply |
| Host backup, read-only rescue, independent emergency DSH | Opens the separate native entry point | Export/repair follows its own scope and authorization; browsing the workbench grants no write permission |

[StartupRecoveryModel](../../app/src/main/java/com/deepseekharness/app/core/StartupRecoveryModel.java) retains its read task across page recreation. Environment-ticket contention retries only reading records, never failed repairs or plugin operations. Multiple pending transactions, changed data identity, or unconfirmed exit retain originals. Do not delete journals to bypass a gate.

Native plugin enable/disable uses [PluginRepository](../../app/src/main/java/com/deepseekharness/app/core/PluginRepository.java) to check `status/name/enabled/intentVerified`, presenting the actual read-back intent first. Full-list refresh is scheduled independently and coalesced, so a later scan does not hide the confirmed result or error. Saved intent takes effect after restarting Web; it does not prove the running process has loaded, unloaded, or become ready. Lists and short enable/disable scripts share [GuestScriptBudget](../../app/src/main/java/com/deepseekharness/app/runtime/GuestScriptBudget.java)'s 30-second cooperative total budget across queueing, preparation checkpoints, and execution. It cannot preempt an individual system I/O, monitor, or Binder wait. Timeout is not proof of exit. Unknown results are not resubmitted, and unconfirmed exit retains the barrier. See [plugin runtime and permissions](plugin-runtime-and-permissions.md) for complete plugin semantics.

## Diagnostics and logs are different actions

“Generate diagnostic report” lets [DiagnosticRepository](../../app/src/main/java/com/deepseekharness/app/core/DiagnosticRepository.java) acquire an environment ticket and run limited probes: device/version, Bash and loader, tool files, smoke test of the selected mode, real Node/npm/Python responses, managed identity, latest trial, free space, current authentication/plugin observations, and host resources. It does not traverse conversations/personal files or read complete logcat, and opening the page does not automatically run expensive probes.

“Repair certificates and npm” is an explicit write action limited to that scope, followed by collection again. Pending maintenance or environment contention rejects it. Repair failure remains a failure even if the subsequent read-only report can be generated. Host FD/PSS/thread samples cover the current native process only, excluding Ubuntu and separate browser children; compare multiple samples after the same operation.

“Download error logs / Save as” lets [ErrorLogRepository](../../app/src/main/java/com/deepseekharness/app/core/ErrorLogRepository.java) independently create a bounded `DSHA-diagnostics-…tar.gz`, without guest, Python, or model credentials. Defaults include structured state, a summary, and an existing redacted operation tail. `manifest.json` records checksums and capture limits with `dataBackup=false` and `automaticUpload=false`. This is not a data backup.

| Save / additional option | When it takes effect | Failure and privacy boundary |
|---|---|---|
| Download logs | A click generates and saves in the background to Download/DSHA | Write/read-back failure is explicit; Save as remains available and the prior usable export location is retained |
| Save as | Writes and reads back after a system document target is selected | Canceling the chooser commits nothing; a Provider error is not “saved” |
| Add context for this export only | If selected for this action, includes only text actively entered by the user | The choice is neither persisted nor restored; 32768-character limit; no automatic business-body capture |
| Copy / export diagnostic text | The user's action outputs the current report and explanation | Redaction recognizes finite formats; review content before public sharing |

The default failure bundle excludes raw process output, conversation bodies, credentials, and full exception chains. Rotated history cannot be reconstructed. [DiagnosticExportArchive](../../app/src/main/java/com/deepseekharness/app/backup/DiagnosticExportArchive.java) allows at most 32 entries, 256 KiB per entry, and a 1 MiB total content budget, in standard tar/gzip with per-entry SHA-256. Reports are not automatically uploaded.

## Record limits and interpretation

| Record | Limit / behavior | What it proves |
|---|---|---|
| Startup timeline | [StartupTrace](../../app/src/main/java/com/deepseekharness/app/util/StartupTrace.java): about 48 Ki characters and 300 lines; each line truncated at 3000 characters; at most 20 issues | Stages/observations within the retained window. Error keywords are related logs, not automatic plugin attribution |
| Recent startups | [StartupHistoryStore](../../app/src/main/java/com/deepseekharness/app/util/StartupHistoryStore.java): latest 5 in a private native directory | Each generation's ready/failed/stopped/interrupted state, not all history |
| App events | [DiagnosticHistory](../../app/src/main/java/com/deepseekharness/app/core/DiagnosticHistory.java): 32 KiB tail; [DiagnosticLog](../../app/src/main/java/com/deepseekharness/app/core/DiagnosticLog.java): about 800 characters per event | Redacted operation stages, not model-message/terminal-input capture |
| Cold-install record | [ColdInstallDiagnostics](../../app/src/main/java/com/deepseekharness/app/core/ColdInstallDiagnostics.java): reads a bounded tail before appending, compacts display to about 8000 characters | Installation stages/failures readable on restricted ROMs, not guaranteed complete raw output |

Backend-authentication and browser-ready times are not pure loading benchmarks. Time spent on Main, manual entry into Web, and browser-observer timing affect the latter. Successful logs from an old APK do not prove a new APK; absence of recorded errors does not prove zero crashes or all plugins passed.
