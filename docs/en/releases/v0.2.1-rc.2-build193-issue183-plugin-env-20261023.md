# DSHA build193 · DSH 0.2.1-rc.3

This Standard update pins the formal managed DSH runtime to **0.2.1-rc.3** and adds application-side accessibility scheduling changes related to issue183, a plugin dependency command fix, and startup diagnostic corrections. The scope below describes software changes and recorded host evidence. Final software results and device limits appear below.

- Diagnostic version: `0.2.1-rc.2-20261023.2047-dsh0.2.1-rc.3`, versionCode **193**.
- Delivery: **Standard / `dsh.android.client` / historical E7E3 release certificate / non-debuggable**.
- The conventional filename remains `dsha-0.2.1-rc.2.apk`; its rc.2 filename does not identify the bundled formal DSH runtime version.

## Changes

**Application scheduling related to issue183.** Accessibility pairing reads now use a dedicated worker with one running read and one latest pending event. Connection epochs, cancellation checks, and the final permit check prevent stale services or cancelled requests from dispatching later. Disconnect and revocation no longer wait for a permit callback to release the service lifecycle lock. Tree expansion has time, node, and depth budgets. Screenshot callback work uses a bounded queue and does not fall back to heavy processing on the framework caller when saturated. Bounded service lifecycle diagnostics are also recorded. These changes constrain application work and queues; they cannot interrupt an Android Binder call already in progress. Unknown results after permit consumption remain non-replayable. They do not establish that an Android16 system or device failure is resolved.

**Plugin pnpm command correction (V3).** The reproduced cause was argument ordering: pnpm 10 forwards `view/info/show` to npm when the command is the first argument. Managed policy flags previously preceded the command and leaked into the metadata preflight, causing pnpm to try executing a binary named `view`. V3 moves only the exact managed flag suffix after the actual command and its arguments. It preserves caller executable-prefix arguments, registry, source spec, and the permitted lifecycle-script settings. This is not classified as a network failure or worked around by disabling Git prepare or other authorized scripts.

**Formal DSH rc.3.** Direct DSH dependencies use exact rc.3 versions and a new lockfile. Clean resolution and installation retained normal peer enforcement without `--force` or `--legacy-peer-deps`. Local patches were checked against actual rc.3 modules and their complete application order, preserving newly added upstream code. Recorded host data fixtures cover selected storage, session, attachment, credential-reference, and Profile read/write/reopen paths. They are not a complete comparison of user device data and do not authorize runtime rollback.

**Independent recovery also upgrades to rc.3, sharing identical archive bytes in the APK.** Following the explicit decision for this delivery, the independent recovery pin also advances to `0.2.1-rc.3`, archive SHA-256 `d77261bf677a83c2440aab7a60cacf9c95876b59777b74f9de4fa6be9c2ba514`. Its bytes match the formal archive, allowing one physical archive in the APK. Recovery keeps its own lock, extracted runtime root, HOME, and workspace; it does not depend on the installed formal rootfs. Its browser recipes remain version-specific and hash-bound, and historical rc.2 recipes are preserved. Because the new rc.3 entry-customization component requires the intentionally disabled plugin manager, that component is disabled only in the recovery Profile. Recovery still exposes only five controlled tools; HTTP tools cannot confirm writes, and repairs require native confirmation and the transaction barriers. Isolated rc.3 raw and managed host candidates passed real extension prepare, emergency workspace, Chromium input, and normal-shutdown checks. Synthetic temporary-key checks found no key in files, sessions, browser persistent storage, cookies, or logs. The final APK deduplication mapping and actual size still require exact artifact gate results.
